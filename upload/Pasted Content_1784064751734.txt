━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. SHARED PRODUCT CATALOG, SHARED INVENTORY POOL
   Products can be shared across companies within an organization
   (product_scope = organization/selective). When shared, inventory
   is ONE POOL per variant per location — never duplicated per
   company. Every stock movement records which company caused it
   (for cost attribution / COGS), but the stock count itself is
   singular and shared.

2. WEIGHTED AVERAGE COST (WAC) — ALREADY WORKING IN PRODUCT SYSTEM
   Every location maintains its own average cost per variant (costs
   can differ by location — e.g. Karachi stock may have cost more
   due to transfer/logistics). New purchases recalculate the average:
   new_avg = (existing_qty × old_avg + new_qty × new_cost) / total_qty
   Cost is LOCKED at the moment of each transaction — never
   retroactively recalculated for past transactions.

3. LOCATIONS CAN BE ORG-LEVEL (SHARED) OR COMPANY-LEVEL (PRIVATE)
   A location with company_id = NULL is a shared organization
   warehouse any company in the org can use (typically for shared
   org-scope products). A location with company_id set belongs
   privately to one company only.

4. STITCHED VS UNSTITCHED — TWO FULFILLMENT MODES ALREADY EXIST
   Variants have fulfillment_type: 'stock_based' (normal tracked
   inventory) or 'made_to_order' (no stock held; produced when an
   order arrives, consuming fabric from a linked stock_based variant).

5. RETURNED MADE-TO-ORDER ITEMS JOIN THE SAME INVENTORY SYSTEM
   There is NO separate table for returned stitched items. When a
   made-to-order item is returned in sellable condition, the system
   creates or updates a NORMAL inventory_pools row for that variant
   at the receiving location, using the same process_inventory_
   transaction() function as any other stock movement. A boolean
   track_inventory flag on the variant flips from FALSE to TRUE the
   first time this happens, and STAYS TRUE permanently afterward —
   it never flips back to FALSE, even if the pool empties to zero.
   This keeps the variant's inventory history consistent and
   queryable through the exact same tables as stock_based variants,
   rather than a parallel system.

   On every new order for a made_to_order variant, the fulfillment
   logic must first check if inventory_pools.available > 0 for that
   variant (across relevant locations). If yes, fulfill from existing
   stock (normal reserve/dispatch, no stitching cost incurred). If
   available = 0, trigger a production order (fresh fabric consumption
   and stitching) as normal made-to-order behavior.

6. FABRIC CONSUMPTION FOR MADE-TO-ORDER PRODUCTION
   Each made_to_order variant is linked to a specific stock_based
   "fabric source" variant (e.g. Stitched Size M draws fabric from
   Unstitched). When a production order starts, one unit of fabric
   is consumed from the fabric source variant's stock at a chosen
   location — this is a normal inventory_transaction, just with a
   distinct type so it's traceable.

7. TRANSPORT/LOGISTICS COST ON TRANSFERS IS NOT MERGED INTO WAC
   When stock is transferred between locations, any transport cost
   incurred is tracked as a SEPARATE logistics expense record — it
   does NOT get added into the receiving location's average cost.
   The transferred stock arrives at the receiving location using the
   exact cost_per_unit it had at the sending location.

8. PURCHASE ORDERS ARE A TWO-STEP PROCESS
   Placing an order with a supplier (creates "incoming" stock
   visibility) is separate from actually receiving the goods (which
   is when WAC recalculates and on_hand actually changes). Partial
   deliveries, quantity discrepancies, and price differences between
   the ordered cost and the actually-invoiced cost must all be
   supported.

9. SUPPLIER RETURNS ARE A SEPARATE FLOW FROM CUSTOMER RETURNS
   When defective/wrong/excess stock is sent BACK to a supplier, this
   reduces on_hand at whatever cost it was carried at (no WAC
   recalculation — the average moves because quantity decreases, but
   using the existing average cost, not a new cost). Resolution can
   be a refund, replacement (a fresh purchase_received event), or a
   credit note (tracked as a running balance against the supplier for
   future purchase orders).

TABLE: inventory_pools
─────────────────────────────
THE single source of truth for stock levels. One row per variant per
location. Never duplicated per company — company attribution lives in
inventory_transactions instead.

  id                    UUID PRIMARY KEY DEFAULT gen_random_uuid()
  org_variant_id        UUID NOT NULL REFERENCES org_product_variants(id) ON DELETE CASCADE
  location_id           UUID NOT NULL REFERENCES inventory_locations(id) ON DELETE CASCADE
  organization_id       UUID NOT NULL REFERENCES organizations(id)

  on_hand               INT NOT NULL DEFAULT 0 CHECK (on_hand >= 0)
  reserved              INT NOT NULL DEFAULT 0 CHECK (reserved >= 0)
  available             INT GENERATED ALWAYS AS (on_hand - reserved) STORED
  incoming              INT NOT NULL DEFAULT 0 CHECK (incoming >= 0)
  -- incoming = sum of undelivered quantity across open purchase_order_items
  --   targeting this variant + location

  avg_cost              NUMERIC(12,4) NOT NULL DEFAULT 0
  total_stock_value     NUMERIC(16,2) GENERATED ALWAYS AS (on_hand * avg_cost) STORED

  reorder_point         INT DEFAULT 0
  reorder_quantity      INT DEFAULT 0

  last_received_at      TIMESTAMPTZ
  last_sold_at          TIMESTAMPTZ
  last_counted_at       TIMESTAMPTZ

  updated_at            TIMESTAMPTZ DEFAULT NOW()

  UNIQUE(org_variant_id, location_id)
  INDEX on (organization_id, org_variant_id)
  INDEX on (location_id)

FUNCTION 2: process_inventory_transaction(...) — THE CORE FUNCTION
  Parameters: org_variant_id, location_id, organization_id, company_id
  (nullable), employee_id, transaction_type, quantity, cost_per_unit
  (nullable — uses current avg_cost if not provided), reference_type,
  reference_id, notes, metadata

  Logic:
    1. Lock the inventory_pools row (SELECT ... FOR UPDATE). If no row
       exists yet for this variant+location, create one first with
       on_hand=0, avg_cost=0 (this happens automatically on the FIRST
       transaction ever for that variant+location pair — including
       the very first return of a made_to_order variant).
    2. Validate: if this is an OUT-direction transaction type
       (sale_dispatched, transfer_out, damage_writeoff, theft_writeoff,
       missing_writeoff, transit_loss, supplier_return,
       fabric_consumed_for_stitching), check available >= ABS(quantity).
       If not, return an error 'INSUFFICIENT_STOCK' — do not proceed.
    3. If transaction_type = 'purchase_received' or
       'return_stitched_received' or 'transfer_in' or 'opening_stock':
       compute new_avg via calculate_new_avg_cost(); use it as
       cost_per_unit if not explicitly passed; update inventory_pools
       .avg_cost to the new value.
    4. If transaction_type = 'transfer_in': cost_per_unit is passed in
       explicitly (the sending location's cost at time of transfer)
       — do NOT let logistics_cost affect this value (see Part 4 rule).
    5. Update inventory_pools.on_hand and/or .reserved based on
       transaction_type per the mapping table below.
    6. If this transaction touches a made_to_order variant with
       track_inventory currently FALSE and the type is
       'return_stitched_received': set track_inventory = TRUE on the
       variant record as part of this same call.
    7. Insert the inventory_transactions row with avg_cost_before/after.
    8. If avg_cost changed: insert avg_cost_history row.
    9. Return { success, transaction_id, new_pool_state }.

  TRANSACTION TYPE → POOL UPDATE MAPPING:
    opening_stock              → on_hand += qty
    purchase_received          → on_hand += qty, incoming -= qty (if PO-linked)
    sale_dispatched            → on_hand -= qty, reserved -= qty
    order_reserved             → reserved += qty
    order_unreserved           → reserved -= qty
    return_resellable          → on_hand += qty
    return_stitched_received    → on_hand += qty (creates pool if needed)
    return_damaged              → no pool change (goes straight to stock_loss_records)
    transfer_out                 → on_hand -= qty
    transfer_in                   → on_hand += qty
    cycle_count_adjust            → on_hand = system_quantity + discrepancy (set directly)
    damage_writeoff/theft_writeoff/missing_writeoff/transit_loss → on_hand -= qty
    supplier_return                → on_hand -= qty
    fabric_consumed_for_stitching   → on_hand -= qty (on the FABRIC variant, not the stitched one)

FUNCTION 3: check_returned_stock_availability(p_variant_id)

CRITICAL RULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. inventory_pools must NEVER be written to directly from a server
   action — only through process_inventory_transaction(). This is
   the single point of truth guaranteeing the ledger and pool always
   agree.

2. track_inventory on a made_to_order variant is a ONE-WAY flag:
   FALSE → TRUE is allowed automatically on first return; TRUE → FALSE
   must never happen through any code path in this system.

3. Transport/logistics cost on transfers is tracked in
   stock_transfers.logistics_cost and NEVER added into the receiving
   location's avg_cost calculation — the transferred stock keeps its
   original cost_per_unit exactly.

4. Every table that represents a financial ledger
   (inventory_transactions, avg_cost_history) is immutable — no
   UPDATE or DELETE policies exist for these under any role.

5. Never hard-delete locations, suppliers, purchase orders, or
   production orders — always use status/is_active flags.

6. This is an ADD-ON to the existing product schema — org_products,
   org_product_variants (aside from the two new columns above),
   company_product_settings, company_variant_pricing, categories,
   brands, and attributes must not be altered beyond what's
   explicitly specified in Part 10.
