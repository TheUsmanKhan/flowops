    37→## 1. Executive Summary
    38→
    39→**FlowOps** is a multi-tenant SaaS ERP built for Pakistani e-commerce businesses. It manages the complete order lifecycle: product catalog → customer management → order creation → inventory reservation → courier booking → dispatch → delivery/RTO → returns/exchanges. It integrates with Pakistani courier services (PostEx, Leopard) for real-time booking and status tracking.
    40→
    41→**Core value proposition**: One system to manage products, inventory, orders, customers, and courier bookings — replacing the spreadsheets + WhatsApp + manual courier portal workflow that Pakistani e-commerce sellers currently use.
    42→
    43→**Scale**: 68 Prisma models, 170+ API routes, ~160 React components (108 non-UI + 52 shadcn/ui), 21 SQL migrations, 30 permission keys, 2 live courier integrations, 5 cron jobs.
    44→
    45→**Performance posture** (as of latest optimization pass):
    46→- First Load JS: **1,070 KB** (down from 3,148 KB baseline — 66% reduction via code-splitting)
    47→- Total JS across all chunks: **4,665 KB** (95 chunks — was 10 chunks pre-split)
    48→- All 70 data-fetching views use TanStack Query (was 64/70 — 6 migrated from raw `useEffect`+`api.get()`)
    49→- `React.memo` used on leaf components in 6 largest views
    50→- 10 dead dependencies removed (node_modules: 1.2 GB, was 1.3 GB)
    51→- Route-aware `LoadingFallback` renders PageHeader text immediately at Suspense boundary
    52→- Idempotency system: `withIdempotency()` + `useIdempotentMutation()` on ALL 24+ creation endpoints
    53→- Phone validation: libphonenumber-js for international phone format validation
    54→- Courier cancel: Leopard cancellation now works (guard removed); order cancellation auto-cancels courier booking
    55→- City propagation: corrected cities propagate back to CustomerAddress
    56→- IntegrationActionLog now logs request payloads (not just responses)

    60→## 2. What FlowOps Is
    61→
    62→### Target User
    63→Pakistani e-commerce sellers (Instagram/Facebook/Daraz/Shopify) who:
    64→- Sell products COD (Cash on Delivery) — the dominant payment method in Pakistan
    65→- Ship via local couriers (PostEx, Leopard, TCS)
    66→- Need to track which orders are confirmed, packed, dispatched, delivered, or returned (RTO)
    67→- Need inventory management (stock-based + made-to-order)
    68→- Need customer management with RTO-rate flagging (high-return customers)
    69→
    70→### Multi-Tenant Model
    71→```
    72→Organization (top-level tenant, owned by one user)
    73→  └── Company (sub-tenant — a brand/store under the org)
    74→        ├── Employees (users with roles/permissions in this company)
    75→        ├── Products (company subscribes to org-level product templates)
    76→        ├── Inventory (company-owned stock in locations)
    77→        ├── Orders (company's orders)
    78→        ├── Customers (org-level, shared across companies in the org)
    79→        └── Integrations (company's courier connections)
    80→```
    81→
    82→A user can belong to multiple companies (via Employee records) and switch between them using the workspace switcher. The active company is stored in `UserSetting.activeCompanyId`.
    83→
    84→### Order Lifecycle (the heart of the system)
    85→```
    86→pending → confirmed → processing → packed → dispatched → delivered
    87→                ↓                                      ↓
    88→         partially_backordered                       rto
    89→                ↓
    90→            cancelled
    91→```
    92→
    93→Every transition has inventory side-effects:
    94→- **Confirm**: reserve stock (`reserved += qty`) or backorder if insufficient
    95→- **Dispatch**: deduct stock (`onHand -= qty`, `reserved -= qty`)
    96→- **Cancel**: unreserve stock (`reserved -= qty`)
    97→- **RTO**: restock (`onHand += qty` via `return_resellable` or `return_stitched_received`)

   169→## 4. Architecture Overview
   170→
   171→### High-Level Data Flow
   172→```
   173→Browser (SPA at /)
   174→  ↓ Authorization: Bearer <token> + cookie
   175→Caddy Gateway (:81 → :3000)
   176→  ↓
   177→Next.js 16 API Routes (148 routes under src/app/api/)
   178→  ↓
   179→Server Actions (src/lib/actions/*.ts)
   180→  ↓
   181→Prisma Client (src/lib/db.ts)
   182→  ↓
   183→Supabase PostgreSQL (Mumbai)
   184→```
   185→
   186→### Key Architectural Decisions
   187→
   188→1. **Single SPA route** — the entire app lives at `/` (`src/app/page.tsx`). Navigation is client-side via Zustand's `navigate(route)` with URL sync. There are no other Next.js pages.
   189→
   190→2. **Custom HMAC sessions** — Sessions are HMAC-signed tokens: `userId.timestamp.hmac` (30-day TTL). Dual-channel: `Authorization: Bearer` header (works in iframes/cross-origin) + HttpOnly cookie fallback. (`next-auth` was previously installed but unused; it was removed in Step 4 — see §3.)
   191→
   192→3. **Multi-tenant isolation in app layer** — `getWorkspace()` in `src/lib/workspace.ts` resolves the caller's active company from `UserSetting.activeCompanyId` via a SINGLE Prisma JOIN query (Profile → settings.activeCompany + employees.role). No database-level RLS — all scoping is enforced in the application layer via `requirePermission()`.
   193→
   194→4. **Fire-and-forget audit/metric writes** — `insertAuditLog()` and `insertMetricEvent()` return `void` immediately (detached promises via `fireAndForget()`). This works because the app runs on a long-lived Bun/Node server where the event loop survives the HTTP response.
   195→
   196→5. **Adapter pattern for couriers** — provider-agnostic `CourierAdapter` interface. Only PostEx + Leopard are real implementations; TCS is a stub. All courier calls go through `executeLoggedIntegrationAction()` which logs every API call to `integration_action_logs`.
   197→
   198→6. **Prisma `db push` workflow** — the `supabase/migrations/*.sql` files are reference SQL. The live schema is managed via `prisma db push` against `prisma/schema.prisma`. SQL functions (like `generate_order_number()`) must be applied manually to the DB.

   360→## 6. Authentication & Multi-Tenancy
   361→
   362→### Session System
   363→- **Token format**: `userId.timestamp.hmac` (HMAC-SHA256 signed)
   364→- **TTL**: 30 days
   365→- **Storage**: `localStorage` key `flowops_session_token` + HttpOnly cookie `flowops_session`
   366→- **Dual-channel**: API client sends BOTH `Authorization: Bearer <token>` header AND cookie — works in iframes, cross-origin, and same-origin
   367→
   368→### Auth Flow
   369→```
   370→1. POST /api/auth/login {email, password}
   371→2. Server: verify scrypt hash → create session token → set cookie + return token
   372→3. Client: store token in localStorage + Zustand store
   373→4. Subsequent requests: send Bearer token + cookie
   374→5. POST /api/auth/logout → clear cookie + localStorage
   375→```

   394→### Workspace Resolution
   395→`getWorkspace()` in `src/lib/workspace.ts`:
   396→- Resolves caller's active company + employee + role in a SINGLE Prisma query (Profile → settings.activeCompany + employees.role)
   397→- Throws `ApiError(401)` if not signed in, `ApiError(403)` if no active company or not a member
   398→- Returns `WorkspaceContext` = `{ user, employee, company }`
   399→- Called by nearly every authenticated API route
   400→
   401→### Session Payload (`src/lib/session-payload.ts`)
   402→`buildSessionPayload()` uses a SINGLE raw SQL JOIN (`prisma.$queryRaw`) that joins Profile + UserSetting + Employee + Company + Role + RolePermission in one statement. Replaces the previous 5-6 sequential Prisma queries. Latency: ~696ms → ~210ms warm (67% faster). The raw query result (flat rows) is grouped in JS back into the nested SessionResponse shape. The old SQL `normalize_phone()` function remains for DB-level triggers/matching; the app-layer path now uses `libphonenumber-js` for phone normalization.
