 11206→### 2. Stock Model (InventoryPool)
 11207→═══════════════════════════════════════════════════════════════════
 11208→**Model:** `InventoryPool` (schema.prisma:1087-1116).
 11209→- Fields: `orgVariantId`, `locationId`, `organizationId`, `onHand`, `reserved`, `incoming`, `avgCost`, `reorderPoint`, `reorderQuantity`, `lastReceivedAt`, `lastSoldAt`, `lastCountedAt`.
 11210→- **Unique constraint: `@@unique([orgVariantId, locationId])`** — there is NO companyId on this model.
 11211→- Indexes: `[organizationId, orgVariantId]`, `[locationId]`.
 11212→
 11213→**Scoping:** Stock is keyed by `organizationId + orgVariantId + locationId`. It is NOT explicitly per-company. Company-level isolation happens INDIRECTLY through `InventoryLocation.companyId` (see area #9): if a location is company-private, its pools are de-facto company-private; if a location is org-shared (companyId=null), its pools are shared across all companies in the org.
 11214→
 11215→**When Company A creates an order, does stock decrease from a pool shared with Company B?**
 11216→- `reserveOrderStock` (order.actions.ts:129) uses `item.reservedLocationId ?? order.dispatchLocationId` (line 161). The `dispatchLocationId` is set on the order at creation (line 712: `dispatchLocationId: d.dispatch_location_id`). The user picks the dispatch location from the locations list returned by `GET /api/inventory-locations` (which returns BOTH org-shared AND company-private — see area #9).
 11217→- If Company A picks an org-shared location, the reservation decrements `available` (onHand - reserved) on a pool that Company B can also see and reserve from. So YES — if companies share an org-level location, they share stock. This is by design.
 11218→- If Company A picks its own company-private location, no cross-company contamination.
 11219→
 11220→**reserveStockForOrder** (inventory.ts:691-736):
 11221→- Takes `{ orgVariantId, locationId, organizationId, companyId, employeeId, quantity, orderId }`.
 11222→- Looks up the pool by `orgVariantId_locationId` unique key.
 11223→- Validates `available >= quantity`.
 11224→- Calls `processInventoryTransaction` with type `order_reserved` (which increments `reserved` only — does NOT touch `onHand`).
 11225→- The `companyId` is recorded on the resulting `InventoryTransaction` ledger row (for attribution/filtering), but the pool itself is company-agnostic.
 11226→
 11227→**unreserveStockForOrder** (inventory.ts:743-768):
 11228→- Same shape as reserveStockForOrder.
 11229→- Calls `processInventoryTransaction` with type `order_unreserved` (decrements `reserved` only).
 11230→
 11231→**performOrderDispatch** (order.actions.ts:2259-2434):
 11232→- Iterates over `orderItem` rows with `fulfillmentStatus: 'reserved'` (line 2330).
 11233→- For each, calls `dispatchInventory({ orgVariantId, locationId: item.reservedLocationId ?? order.dispatchLocationId, organizationId, companyId, employeeId, quantity, orderId })` at line 2342.
 11234→- `dispatchOrder` (inventory.ts:775-801) calls `processInventoryTransaction` with type `sale_dispatched`. That type:
 11235→  - Decrements `onHand` by absQty.
 11236→  - Decrements `reserved` by absQty (releases the reservation).
 11237→  - Uses `costPerUnit: null` → falls back to the pool's current `avgCost` (COGS locked at dispatch time).
 11238→- So **YES, onHand is decremented at dispatch time**, from the pool identified by `[orgVariantId, reservedLocationId]` (which was set at reservation time).
 11239→
 11240→**Cross-company contamination risk:** Only if companies share an org-level location. If each company uses its own company-private location for dispatch, pools are isolated.

 11242→**Functional status:** Fully functional (reservation at confirmation, dispatch deduction, COGS locking via WAC).

 11246→═══════════════════════════════════════════════════════════════════

 11248→
 11249→**Behavior:**
 11250→1. Fetches the order with items + their `orgVariant` (line 839-855).
 11251→2. Uses `order.dispatchLocationId` as the restock location (line 858 — SAME pool stock was originally taken from at dispatch time).
 11252→3. For each item with `fulfillmentStatus === 'dispatched'` (line 870):
 11253→   - Recovers cost-per-unit from the original `sale_dispatched` transaction (line 873-884, finds it by `orgVariantId + locationId + transactionType='sale_dispatched' + referenceType='order' + referenceId=orderId`).

 11258→4. For each item with `fulfillmentStatus === 'reserved'` (not yet dispatched — line 917): just calls `unreserveStockForOrder` (releases the reservation, no onHand change).

 11261→**Manual RTO path** (`processOrderReturn` at order-return.actions.ts:52-219):
 11262→- Called from `POST /api/orders/[id]/rto`.

 11270→**Cross-company contamination risk:** NONE within the restock path itself. The order being RTO'd is found by ID (in the webhook/poller path) or by `companyId` (in the manual UI path). Stock goes back to the same pool it came out of. The companyId on the new return transaction is the order's companyId.

 11399→═══════════════════════════════════════════════════════════════════

 11405→
 11406→**Is the cycle count functional (actually adjusts stock) or just frontend display?**
 11407→**FULLY FUNCTIONAL.** The PATCH route (`/api/cycle-counts/[id]`) supports 4 actions:
 11408→1. **`start`** (line 130-168): Snapshots all current `inventory_pools` at the location into `CycleCountItem` rows (systemQuantity = pool.onHand, discrepancyValue = pool.avgCost). Sets status='in_progress'.

 11410→3. **`approve`** (line 222-350): Actually creates adjustment transactions:
 11411→   - For each item with `countedQuantity !== null` and `discrepancy !== 0`:
 11412→     - If shortage AND `discrepancyReason` is `theft_suspected` or `unknown`: calls `quarantineStock` (reserves the missing quantity) + creates a `StockLossRecord` with `lossType='missing', subType='suspected', investigationStatus='open'` (line 237-267).  11468→## Cross-Cutting Observations
 11469→═══════════════════════════════════════════════════════════════════
 11470→
 11471→1. **The fundamental design choice:** InventoryPool is keyed by `[orgVariantId, locationId]` with NO companyId. Company isolation is achieved INDIRECTLY via InventoryLocation.companyId. This means:
 11472→   - If a company uses ONLY its own private locations → full stock isolation.
 11473→   - If a company uses org-shared locations → stock at those locations is shared (intentional for shared warehouses).
 11474→   - The InventoryTransaction ledger DOES carry companyId for attribution/filtering, but the pool state (onHand, reserved, avgCost) is shared.
 11475→
 11476→2. **Location-ownership validation gap (low severity, defense-in-depth):** Several mutation routes (PO create, stock loss report, stock adjust, cycle count create) verify that the user is authenticated + has permission, but they DO NOT verify that the `location_id` (or `delivery_location_id`) belongs to the active company. The UI only exposes the active company's locations (own + org-shared), so this is not exploitable through normal UI flows, but a malicious actor with direct API access could target another company's private location.
 11477→
 11478→3. **Pricing seed gap (known):** `POST /api/products` and `POST /api/products/[id]/variants` write to CompanyVariantPricing (legacy) but NOT to MarketVariantPricing. So freshly-created variants have no MVP row in the Default market, causing createManualOrder to reject orders with gate-3 until the user explicitly sets a price via the Pricing tab. (Worklog line 11073 confirms CVP is "deprecated for pricing, read once for seed".)
 11479→
 11480→4. **Stock adjustment positive-direction bug:** `POST /api/inventory/adjust` uses `cycle_count_adjust` for positive adjustments, which SETS onHand to the value (not increments). So a +5 adjustment on a pool with onHand=10 results in onHand=5, not onHand=15. Negative adjustments work correctly (use `damage_writeoff` which decrements). This is a real bug worth fixing.
 11481→
 11482→5. **Production order → order dispatch automation gap:** When a ProductionOrder is marked "completed" or "dispatched" via PATCH, nothing triggers on the linked OrderItem. The OrderItem stays at `fulfillmentStatus='reserved'` until the user manually triggers `performOrderDispatch`. Furthermore, MTO fresh-produced items never had a pool to dispatch from — `performOrderDispatch` calls `dispatchOrder` (type `sale_dispatched`), which expects to decrement onHand from a pool. For an MTO item that was fresh-produced, this would either fail (no pool exists) or erroneously decrement some other pool's onHand (if a returned-stock pool exists for the same variant+location). The cycle is not closed.
 11483→
 11484→6. **Inventory dashboard is org-wide:** `GET /api/inventory/dashboard` filters by `organizationId` only (no companyId). In a multi-company org, this conflates stock from all companies into one total. This is consistent with the org-level pool design but may surprise users expecting per-company totals.
 11485→
 11486→7. **Idempotency:** PO create, loss report (damaged), cycle count create, supplier return create, location create, and stock adjust all support `Idempotency-Key` header via `withIdempotency()`. Order actions (createManualOrder, cancelOrder, createOrderFromShopifyWebhook) do NOT use idempotency keys (webhook order ingestion has its own externalOrderId check instead).
