    20→
    21→1. SHARED PRODUCT CATALOG, SHARED INVENTORY POOL
    22→   Products can be shared across companies within an organization
    23→   (product_scope = organization/selective). When shared, inventory
    24→   is ONE POOL per variant per location — never duplicated per
    25→   company. Every stock movement records which company caused it
    26→   (for cost attribution / COGS), but the stock count itself is
    27→   singular and shared.
    28→
    29→2. WEIGHTED AVERAGE COST (WAC) — ALREADY WORKING IN PRODUCT SYSTEM
    30→   Every location maintains its own average cost per variant (costs
    31→   can differ by location — e.g. Karachi stock may have cost more
    32→   due to transfer/logistics). New purchases recalculate the average:
    33→   new_avg = (existing_qty × old_avg + new_qty × new_cost) / total_qty
    34→   Cost is LOCKED at the moment of each transaction — never
    35→   retroactively recalculated for past transactions.
    36→
    37→3. LOCATIONS CAN BE ORG-LEVEL (SHARED) OR COMPANY-LEVEL (PRIVATE)
    38→   A location with company_id = NULL is a shared organization
    39→   warehouse any company in the org can use (typically for shared
    40→   org-scope products). A location with company_id set belongs
    41→   privately to one company only.
    42→
    43→4. STITCHED VS UNSTITCHED — TWO FULFILLMENT MODES ALREADY EXIST
    44→   Variants have fulfillment_type: 'stock_based' (normal tracked
    45→   inventory) or 'made_to_order' (no stock held; produced when an
    46→   order arrives, consuming fabric from a linked stock_based variant).
    47→
    48→5. RETURNED MADE-TO-ORDER ITEMS JOIN THE SAME INVENTORY SYSTEM
    49→   There is NO separate table for returned stitched items. When a
    50→   made-to-order item is returned in sellable condition, the system
    51→   creates or updates a NORMAL inventory_pools row for that variant
    52→   at the receiving location, using the same process_inventory_
    53→   transaction() function as any other stock movement. A boolean
    54→   track_inventory flag on the variant flips from FALSE to TRUE the
    55→   first time this happens, and STAYS TRUE permanently afterward —
    56→   it never flips back to FALSE, even if the pool empties to zero.
    57→   This keeps the variant's inventory history consistent and
    58→   queryable through the exact same tables as stock_based variants,
    59→   rather than a parallel system.
    60→
    61→   On every new order for a made_to_order variant, the fulfillment
    62→   logic must first check if inventory_pools.available > 0 for that
    63→   variant (across relevant locations). If yes, fulfill from existing
    64→   stock (normal reserve/dispatch, no stitching cost incurred). If
    65→   available = 0, trigger a production order (fresh fabric consumption
    66→   and stitching) as normal made-to-order behavior.
    67→
    68→6. FABRIC CONSUMPTION FOR MADE-TO-ORDER PRODUCTION
    69→   Each made_to_order variant is linked to a specific stock_based
    70→   "fabric source" variant (e.g. Stitched Size M draws fabric from
    71→   Unstitched). When a production order starts, one unit of fabric
    72→   is consumed from the fabric source variant's stock at a chosen
    73→   location — this is a normal inventory_transaction, just with a
    74→   distinct type so it's traceable.
    75→
    76→7. TRANSPORT/LOGISTICS COST ON TRANSFERS IS NOT MERGED INTO WAC
    77→   When stock is transferred between locations, any transport cost
    78→   incurred is tracked as a SEPARATE logistics expense record — it
    79→   does NOT get added into the receiving location's average cost.
    80→   The transferred stock arrives at the receiving location using the
    81→   exact cost_per_unit it had at the sending location.
    82→
    83→8. PURCHASE ORDERS ARE A TWO-STEP PROCESS
    84→   Placing an order with a supplier (creates "incoming" stock
    85→   visibility) is separate from actually receiving the goods (which
    86→   is when WAC recalculates and on_hand actually changes). Partial
    87→   deliveries, quantity discrepancies, and price differences between
    88→   the ordered cost and the actually-invoiced cost must all be
    89→   supported.
    90→
    91→9. SUPPLIER RETURNS ARE A SEPARATE FLOW FROM CUSTOMER RETURNS
    92→   When defective/wrong/excess stock is sent BACK to a supplier, this
    93→   reduces on_hand at whatever cost it was carried at (no WAC
    94→   recalculation — the average moves because quantity decreases, but
    95→   using the existing average cost, not a new cost). Resolution can
    96→   be a refund, replacement (a fresh purchase_received event), or a
    97→   credit note (tracked as a running balance against the supplier for
    98→   future purchase orders).

   677→FUNCTION 1: calculate_new_avg_cost(p_variant_id, p_location_id,
   678→  p_new_quantity, p_new_unit_cost) RETURNS NUMERIC
   679→  Standard WAC formula, as already used in the product system.
   680→
   681→FUNCTION 2: process_inventory_transaction(...) — THE CORE FUNCTION
   682→  Parameters: org_variant_id, location_id, organization_id, company_id
   683→  (nullable), employee_id, transaction_type, quantity, cost_per_unit
   684→  (nullable — uses current avg_cost if not provided), reference_type,
   685→  reference_id, notes, metadata
   686→
   687→  Logic:
   688→    1. Lock the inventory_pools row (SELECT ... FOR UPDATE). If no row
   689→       exists yet for this variant+location, create one first with
   690→       on_hand=0, avg_cost=0 (this happens automatically on the FIRST
   691→       transaction ever for that variant+location pair — including
   692→       the very first return of a made_to_order variant).
   693→    2. Validate: if this is an OUT-direction transaction type
   694→       (sale_dispatched, transfer_out, damage_writeoff, theft_writeoff,
   695→       missing_writeoff, transit_loss, supplier_return,
   696→       fabric_consumed_for_stitching), check available >= ABS(quantity).
   697→       If not, return an error 'INSUFFICIENT_STOCK' — do not proceed.
   698→    3. If transaction_type = 'purchase_received' or
   699→       'return_stitched_received' or 'transfer_in' or 'opening_stock':
   700→       compute new_avg via calculate_new_avg_cost(); use it as
   701→       cost_per_unit if not explicitly passed; update inventory_pools
   702→       .avg_cost to the new value.
   703→    4. If transaction_type = 'transfer_in': cost_per_unit is passed in
   704→       explicitly (the sending location's cost at time of transfer)
   705→       — do NOT let logistics_cost affect this value (see Part 4 rule).
   706→    5. Update inventory_pools.on_hand and/or .reserved based on
   707→       transaction_type per the mapping table below.
   708→    6. If this transaction touches a made_to_order variant with
   709→       track_inventory currently FALSE and the type is
   710→       'return_stitched_received': set track_inventory = TRUE on the
   711→       variant record as part of this same call.
   712→    7. Insert the inventory_transactions row with avg_cost_before/after.
   713→    8. If avg_cost changed: insert avg_cost_history row.
   714→    9. Return { success, transaction_id, new_pool_state }.
   715→
   716→  TRANSACTION TYPE → POOL UPDATE MAPPING:
   717→    opening_stock              → on_hand += qty
   718→    purchase_received          → on_hand += qty, incoming -= qty (if PO-linked)
   719→    sale_dispatched            → on_hand -= qty, reserved -= qty
   720→    order_reserved             → reserved += qty
   721→    order_unreserved           → reserved -= qty
   722→    return_resellable          → on_hand += qty
   723→    return_stitched_received    → on_hand += qty (creates pool if needed)
   724→    return_damaged              → no pool change (goes straight to stock_loss_records)
   725→    transfer_out                 → on_hand -= qty
   726→    transfer_in                   → on_hand += qty
   727→    cycle_count_adjust            → on_hand = system_quantity + discrepancy (set directly)
   728→    damage_writeoff/theft_writeoff/missing_writeoff/transit_loss → on_hand -= qty
   729→    supplier_return                → on_hand -= qty
   730→    fabric_consumed_for_stitching   → on_hand -= qty (on the FABRIC variant, not the stitched one)

   817→CRITICAL RULES
   818→━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   819→
   820→1. inventory_pools must NEVER be written to directly from a server
   821→   action — only through process_inventory_transaction(). This is
   822→   the single point of truth guaranteeing the ledger and pool always
   823→   agree.
   824→
   825→2. track_inventory on a made_to_order variant is a ONE-WAY flag:
   826→   FALSE → TRUE is allowed automatically on first return; TRUE → FALSE
   827→   must never happen through any code path in this system.
   828→
   829→3. Transport/logistics cost on transfers is tracked in
   830→   stock_transfers.logistics_cost and NEVER added into the receiving
   831→   location's avg_cost calculation — the transferred stock keeps its
   832→   original cost_per_unit exactly.
   833→
   834→4. Every table that represents a financial ledger
   835→   (inventory_transactions, avg_cost_history) is immutable — no
   836→   UPDATE or DELETE policies exist for these under any role.
   837→
   838→5. Never hard-delete locations, suppliers, purchase orders, or
   839→   production orders — always use status/is_active flags.
