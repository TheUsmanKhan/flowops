   208→## 17. Key Conventions & Patterns
   209→
   210→### Naming
   211→- **Tables**: PascalCase (Prisma default) — `Order`, `OrderItem`, `InventoryPool`
   212→- **Columns**: camelCase (Prisma default) — `flowopsOrderNumber`, `courierSubStatus`
   213→- **API routes**: kebab-case — `/api/booking-workbench/bookable`
   214→- **Files**: kebab-case — `order.actions.ts`, `postex.adapter.ts`
   215→- **Components**: PascalCase — `OrderDetailView`, `BookingWorkbenchView`
   216→
   217→### Status Enums (all plain strings, no DB enums)
   218→- **Order.status**: `pending | confirmed | partially_backordered | processing | dispatched | delivered | rto | cancelled | refunded`
   219→- **OrderItem.fulfillmentStatus**: `pending | reserved | backordered | dispatched | returned`
   220→- **courierSubStatus**: `slip_generated | pickup_requested | picked_up | at_warehouse | en_route | out_for_delivery | delivered | returned | out_for_return | attempted | under_review | cancelled_by_merchant | expired`
   221→- **courierBookingStatus**: `not_booked | booked | failed | cancelled`
   222→- **paymentStatus**: `cod_pending | advance_paid | fully_prepaid | cod_collected`
   223→- **fulfillmentType**: `stock_based | made_to_order`
   224→- **inventoryPolicy**: `deny | continue`
   225→
   226→### Fire-and-Forget Pattern
   227→```typescript
   228→// insertAuditLog + insertMetricEvent return void immediately
   229→// The DB write happens on the event loop AFTER the response is sent
   230→insertAuditLog({ action: 'order.created', ... })  // no await!
   231→insertMetricEvent({ metricKey: 'order.created', ... })  // no await!
   232→```
   233→
   234→### Workspace Context Pattern
   235→```typescript
   236→// Every authenticated API route starts with:
   237→const ctx = await getWorkspace()  // resolves user + employee + company
   238→await requirePermission(ctx, PERMISSIONS.ORDERS_CREATE)  // throws 403 if lacking
   239→```
   240→
   241→### Adapter Pattern
   242→```typescript
   243→// Never call adapter methods directly — always through executeLoggedIntegrationAction:
   244→const result = await executeLoggedIntegrationAction({
   245→  companyIntegrationId: integration.id,
   246→  organizationId: ctx.company.organizationId,
   247→  actionType: 'book_shipment',
   248→  direction: 'outbound',
   249→  fn: async () => adapter.bookShipment(bookInput),
   250→})
   251→// This logs the call to IntegrationActionLog + handles errors
   252→```
   253→
   254→### Idempotency
   255→- `reserveOrderStock` skips items with `fulfillmentStatus === 'reserved'` or `'dispatched'`
   256→- `performOrderDispatch` skips items already `'dispatched'`
   257→- `restockOrderForRto` skips items already `'returned'`
   258→- `processInventoryTransaction` validates stock before mutating
   259→
   260→### Creation Idempotency (withIdempotency pattern)
   261→```typescript
   262→// ALL creation endpoints wrap their action in withIdempotency():
   263→const { result, wasReplay } = await withIdempotency({
   264→  key: idempotencyKey,          // from Idempotency-Key header
   265→  companyId: ctx.company.id,
   266→  employeeId: ctx.employee.id,
   267→  actionType: 'order.create',   // or 'product.create', 'customer.create', etc.
   268→  fn: async () => { /* actual creation logic */ },
   269→})
   270→// DB unique constraint on key enforces atomicity — no race window
   271→// Failed attempts can be retried with the same key
   272→// Stale 'processing' rows (>60s) auto-recover
   273→```
   274→
   275→### Phone Validation (libphonenumber-js)
   276→```typescript
   277→// Client-side: isValidPhoneFormat(phone) blocks submission
   278→// Server-side: validateAndNormalizePhone(phone) returns { isValid, normalized }
   279→// External platform: isValidFormat=false on CustomerPhone row (not blocked)
   280→// International: normalize_phone() SQL has pass-through fix for + non-PK numbers
   281→// matchOrCreateExternalCustomer: pre-normalizes international numbers via libphonenumber-js before SQL call
   282→import { isValidPhoneFormat, validateAndNormalizePhone } from '@/lib/phone-validation'
   283→```
   284→
   285→### Country System
   286→- `CustomerAddress.country` + `Order.deliveryCountry` store ISO 3166-1 alpha-2 codes (e.g. "PK", "GB"), defaulting to "PK"
   287→- `CountrySelector` component (reusable) returns alpha-2 codes directly
   288→- Non-PK addresses skip courier city-matching (matchCity, revalidateCityAtBookingTime, validateCustomerAddressCity all early-return for non-PK)
   289→- Phone validation uses the address's country as a HINT for no-`+`-prefix numbers (never a hard rule)
   290→- Shopify fallback: `country_code → countryNameToCode(country) → customer.addresses[0].country → Company.countryCode → 'PK'`
   291→
   292→### Self-Fulfilled Channel
   293→- `Order.fulfillmentChannel`: `'courier' | 'self_fulfilled'` (default `'courier'`)
   294→- Auto-defaults to `'self_fulfilled'` when `deliveryCountry !== 'PK'` (always overridable)
   295→- `generate_self_fulfilled_reference(companyId)` SQL: per-company MAX-based `SF-YYYY-NNNNN`
   296→- Self-fulfilled orders skip auto-booking + city-courier-matching entirely
   297→- Internal slip PDF: jsbarcode CODE128 barcode → SVG → sharp → PNG → @react-pdf/renderer
   298→- `processScan()` resolves via `OR: [trackingNumber, selfFulfilledReferenceNumber]`
   299→- Fully independent of the Markets system (no code coupling)
   300→
   301→### Markets System (3-Gate Enforcement)
   302→- **Gate 1**: `OrgProductVariant.isActive` — toggled-off variants appear DISABLED in picker (not hidden)
   303→- **Gate 2**: `MarketProduct` enablement for the resolved market
   304→- **Gate 3**: `MarketVariantPricing` exists for this variant + resolved market
   305→- First failing reason only (priority: gate 1 → 2 → 3)
   306→- Manual orders: blocked if country not in any market (server-side rejection)
   307→- External orders: NEVER blocked — flagged with `needsReview` + `needsReviewReason`
   308→- Payment types restricted to market's `allowedPaymentTypes` (client + server enforcement)
   309→- No fallback anywhere — a variant with no explicit market price is simply not sellable
   310→
   311→### Pricing Resolution (Discount Rework)
   312→- `unit_price` is NO LONGER accepted from the client (removed from schema)
   313→- Server resolves `originalUnitPrice` STRICTLY from `MarketVariantPricing` for the resolved market
   314→- If no MVP row exists → server REJECTS with gate-3 error (no CompanyVariantPricing/costPrice fallback)
   315→- Per-item discount (`discountType`/`discountValue`): percentage (0-100) or fixed (≤ originalUnitPrice), clamped at 0
   316→- `unitPrice = originalUnitPrice - discount` (final charged price)
   317→- `Order.discountAmount`/`discountReason` (order-wide flat discount) works independently
   318→
   319→### Currency Revenue Rollup
   320→- `computeRevenueWithCurrencies(companyId, orders, baseCurrency)` in `src/lib/analytics/revenue.ts`
   321→- Returns: `{ perCurrency: Map, estimatedTotalBase, baseCurrency, estimateComplete }`
   322→- Per-currency breakdown is always accurate (raw sums, no conversion)
   323→- Estimated total uses latest `ExchangeRateSnapshot` — display only, never touches stored prices
   324→- Used by all 3 revenue sites: orders-view (via `/api/orders/revenue-summary`), order-funnel.ts, customer.actions.ts

   328→## 18. Known Issues & Gotchas
   329→
   330→### Environment
   331→1. **`.env` reverts to SQLite** — the `predev` script guards against this, but always verify before starting. If it happens, restore from DOCKER.md reference or git history.
   332→2. **DB latency** — Mumbai region (~100ms per query from sandbox). Performance optimizations (fire-and-forget, parallel queries, single-JOIN getWorkspace) have been applied. `/api/auth/me` is now ~210ms (was 500-1000ms) — FIXED (see item 14 for details).
   333→3. **Turbopack instability** — dev server can hang during compilation in the sandbox (memory issue). Clear `.next/` cache and restart.
   334→4. **Hydration mismatch from browser extensions** — Grammarly injects `data-gr-ext-installed` + `data-new-gr-c-s-check-loaded` attributes into `<body>`. Fixed via `suppressHydrationWarning` on `<body>` in `layout.tsx`. If new hydration errors appear, check for other browser-extension-injected attributes.
   335→
   336→### Bundling
   337→5. **Do NOT add module-scope `import()` maps** — a `ROUTE_CHUNK_LOADERS` map with 55 `() => import(...)` entries caused Turbopack to create 55 duplicate chunks (+1,303 KB). The ONLY place each route's code should be imported is the `dynamic()` call in `page.tsx`. See §11.1 warning.
   338→
   339→### Integrations
   340→6. **PostEx bulk tracking API** — intermittently returns HTTP 400. Handled with single-track fallback
   341→7. **Vercel cron doesn't fire** — on long-lived server. In-process pollers added for PostEx (30min) + exchange rate refresh (24h). Other crons (city sync, scan reports, Leopard safety-net) need manual triggering or external scheduler. The `ENABLE_IN_PROCESS_POLLER` + `ENABLE_IN_PROCESS_FX_REFRESH` env vars (default `true`) can disable for multi-replica deployments.
   342→8. **PostEx API lag** — parcels may be physically picked up but PostEx's API still shows "Booked" for hours. This is a PostEx issue, not FlowOps
   343→
   344→### Schema
   345→9. **SQL functions must be applied manually** — `generate_order_number()`, `generate_self_fulfilled_reference()`, `normalize_phone()` (with international pass-through fix), `match_or_create_customer()` (now 7 params), etc. are NOT in the Prisma schema. They must be applied via raw SQL to the DB. A consolidated file `supabase/functions-only.sql` contains all 24+ functions + 2 sequences + 12 triggers + 2 partial unique indexes (`invitation_pending_email_unique` + `market_one_default_per_company`).
   346→10. **No DB-level RLS** — all multi-tenant isolation is in the app layer. A bug in `getWorkspace()` or a missing `companyId` filter could leak data across tenants
   347→11. **No `available` column** — `available = onHand - reserved` is computed in app code every time
   348→12. **Order-create child components are module-level functions** — `CustomerSection`, `ItemsSection`, `PaymentSection`, etc. in `order-create-view.tsx` are declared at the module level (NOT closures inside `OrderCreateView`). Any new state variable used in these child components MUST be passed as a prop — referencing it directly will compile fine but crash at runtime with `ReferenceError`. TypeScript does NOT catch this. When adding new state/hooks to `OrderCreateView` that child components need, always: (1) add it to the child's destructured props, (2) add it to the child's type definition, (3) pass it from `<OrderCreateView>` to `<ChildComponent>`.
   349→
   350→### Performance
   351→13. **Audit/metric writes are fire-and-forget** — on a serverless platform (Vercel Edge), these would be killed mid-flight. The current long-lived Bun server keeps them alive
   352→14. **`executeLoggedIntegrationAction` has a blocking DB write** — the `IntegrationActionLog` insert in the `finally` block is awaited (~150ms per booking). Not yet converted to fire-and-forget
   353→15. ~~**`/api/auth/me` takes 500-1000ms**~~ **FIXED (Phase 1 + Phase 2)**: `buildSessionPayload()` now uses a single raw SQL JOIN (`prisma.$queryRaw`) instead of 5-6 sequential Prisma queries. Latency reduced from ~696ms avg to ~210ms warm (67% faster). The raw query JOINs Profile + UserSetting + Employee + Company + Role + RolePermission in one statement. See `src/lib/session-payload.ts`. Phase 2: client-side stale-while-revalidate caching added via TanStack Query (`refetchOnWindowFocus: true` scoped to session query only — see §11.1). Server-side in-memory cache deliberately deferred (see §16 item 19 note).
   354→16. **Booking-time city corrections were not persisted** (FIXED) — `order.update` in `bookOrderWithCourier()` now includes `deliveryCity` + `deliveryAddress`. Pre-fix, corrected cities were sent to the courier API but not saved on the Order row. Historical data cannot be backfilled (requestPayload was null for pre-fix logs). Going forward, requestPayload is logged for all outbound calls.
   355→17. **Employee invite had race window** (FIXED) — was check-then-create (findFirst then create). Now has partial unique index `invitation_pending_email_unique` on `(companyId, invitedEmail) WHERE status='pending'` + catches P2002 constraint violation.
   356→18. **Company integration had race window** (FIXED) — was find-then-create. Now has `@@unique([companyId, providerId])` + catches P2002 → re-fetches + reactivates.
