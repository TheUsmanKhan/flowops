    41→    41→## 1. Executive Summary
    42→    42→
    43→    43→### What FlowOps is
    44→    44→
    45→    45→FlowOps is a multi-tenant SaaS ERP built for **Pakistani e-commerce sellers**. It manages the complete operational lifecycle of a COD-first e-commerce business:
    46→    46→
    47→    47→```
    48→    48→Product catalog → Inventory → Customer → Order → Courier booking →
    49→    49→Dispatch → Delivery / RTO → Returns / Exchanges → Reporting
    50→    50→```
    51→    51→
    52→    52→The platform replaces the patchwork of spreadsheets, WhatsApp threads, and manual courier portals that Pakistani sellers currently stitch together to run their operations.
    53→    53→
    54→    54→### Who it is for
    55→    55→
    56→    56→The target user is a Pakistani e-commerce seller who:
    57→    57→
    58→    58→- Sells on Instagram, Facebook, Daraz, Shopify, or their own storefront.
    59→    59→- Ships COD (Cash on Delivery) — the dominant payment method in Pakistan (~95% of e-commerce).
    60→    60→- Ships via local couriers — PostEx, Leopard Couriers, TCS (the three providers FlowOps integrates).
    61→    61→- Needs to track every order through its lifecycle: confirmed → packed → dispatched → delivered / RTO (Return to Origin).
    62→    62→- Needs inventory management with two fulfillment models: **stock-based** (pre-made stock) and **made-to-order** (stitched on demand, with fabric consumption).
    63→    63→- Needs customer management with RTO-rate flagging (sellers refuse service to high-return customers).
    64→    64→- Operates one or more brands/companies under a single organization (multi-brand operator).
    65→    65→
    66→    66→### What problem it solves
    67→    67→
    68→    68→| Pain point (before FlowOps) | FlowOps solution |
    69→    69→|---|---|
    70→    70→| Orders tracked in WhatsApp + Excel — no single source of truth | Centralized `Order` table with full lifecycle + audit log |
    71→    71→| Courier bookings done manually on each courier's portal | Auto-booking via `bookOrderWithCourier()` + Booking Workbench for bulk |
    72→    72→| Order status updates require manually refreshing courier sites | Auto-poller every 30 minutes (PostEx) + Leopard webhook receiver |
    73→    73→| Inventory counted by hand at month-end | Real-time `InventoryPool` with append-only ledger + WAC cost tracking |
    74→    74→| RTO returns lost track of who returned what | RTO review queue + per-item condition correction + stock loss recording |
    75→    75→| Customer return rates invisible | `Customer.isFlagged` auto-set at 3+ RTO with `flagReason = 'High RTO rate'` |
    76→    76→| Multi-brand operators maintain separate spreadsheets per brand | One org → many companies; user switches workspace with a dropdown |
    77→    77→| Made-to-order stitching has no fabric tracking | `ProductionOrder` model + `fabric_consumed_for_stitching` ledger transaction |
    78→    78→| Stock losses recorded ad-hoc (often missing) | Unified `recordStockLoss()` helper + DB dedup index — see §5 |
    79→    79→| Permutations of who can do what in each module | 30-key permission system + 4 elevated-role bypass — see §5 |

    99→    99→### The order lifecycle (the heart of the system)
   100→   100→
   101→   101→Every order moves through the state machine below. Every transition has an inventory side-effect that runs through the unified `processInventoryTransaction()` ledger.
   102→   102→
   103→   103→```
   104→   104→                      ┌──────────────────────────────────────────────────────────┐
   105→   105→                      │                                                          │
   106→   106→                      ▼                                                          │
   107→   107→   pending ──► confirmed ──► processing ──► packed ──► dispatched ──► delivered   │
   108→   108→                  │                                                  │            │
   109→   109→                  │                                                  ▼            │
   110→   110→                  ▼                                               returned ◄──────┘
   111→   111→            cancelled                                  (RTO → auto-restock)
   112→   112→                  ▲
   113→   113→                  │
   114→   114→            partially_backordered
   115→   115→                  │
   116→   116→                  ▼
   117→   117→            cancelled
   118→   118→```
   119→   119→
   120→   120→**Inventory side-effects per transition**:
   121→   121→
   122→   122→| Transition | Inventory effect | Ledger transaction type |
   123→   123→|---|---|---|
   124→   124→| `pending → confirmed` | reserve stock for each line item | `order_reserved` (decreases available, doesn't touch onHand) |
   125→   125→| `pending → cancelled` | none (nothing reserved yet) | — |
   126→   126→| `confirmed → partially_backordered` | reserve available, backorder remainder | `order_reserved` (partial) + `OrderItem.fulfillmentStatus = 'backordered'` |
   127→   127→| `confirmed → processing` | none (operational marker) | — |
   128→   128→| `processing → packed` | none (operational marker) | — |
   129→   129→| `confirmed/processing/packed → dispatched` | deduct stock + release reservation | `sale_dispatched` (decreases onHand + reserved, locks COGS at avgCost) |
   130→   130→| `dispatched → delivered` | none (operational marker) | — |
   131→   131→| `dispatched → returned` (RTO) | restock returned items | `return_resellable` or `return_stitched_received` (increases onHand) |
   132→   132→| `dispatched → cancelled` | blocked — post-dispatch cancellation not allowed | — |
   133→   133→
   134→   134→### The multi-tenant model
   135→   135→
   136→   136→```
   137→   137→Organization (top-level tenant, owned by one user — the Org Owner)
   138→   138→  │
   139→   139→  └── Company (sub-tenant — a brand or store under the org)
   140→   140→        │
   141→   141→        ├── Employees (users with roles/permissions in this company)
   142→   142→        ├── Products (company SUBSCRIBES to org-level product templates)
   143→   143→        ├── Inventory (company-owned stock in its own locations)
   144→   144→        ├── Orders (company's orders — company-scoped)
   145→   145→        ├── Customers (org-level, shared across companies in the org)
   146→   146→        └── Integrations (company's own courier connections)
   147→   147→```
   148→   148→
   149→   149→A user can belong to multiple companies (via `Employee` records) and switch between them using the workspace switcher. The active company is stored in `UserSetting.activeCompanyId` and resolved on every API call by `getWorkspace()` (see §3 and §5).
   150→   150→
   151→   151→### Why custom, not off-the-shelf
   152→   152→
   153→   153→FlowOps was built custom (rather than on Shopify, Odoo, or Erpnext) because:
   154→   154→
   155→   155→1. **Pakistani courier integrations** — PostEx and Leopard have non-standard REST APIs with quirks (Leopard uses 2-character status codes; PostEx bulk tracking intermittently returns HTTP 400). Off-the-shelf ERPs don't support these.
   156→   156→2. **COD-first payment model** — most ERPs assume prepaid/card payment as the default. FlowOps treats COD as the default with optional prepaid.
   157→   157→3. **Multi-brand with shared catalog** — the org/company split (org owns catalog, companies subscribe) is unusual; most multi-tenant ERPs have one tenant = one catalog.
   158→   158→4. **Made-to-order stitching** — fabric consumption + returned-stitched bucket reuse is a niche workflow specific to Pakistani apparel sellers.

   245→   245→## 3. Architecture Overview
   246→   246→
   247→   247→FlowOps is a single-page Next.js app with a thin API layer over Supabase PostgreSQL. All business logic lives in server action files — API routes are thin wrappers.
   248→   248→
   249→   249→### 3.1 High-level data flow
   250→   250→
   251→   251→```
   252→   252→┌────────────────────────────────────────────────────────────────┐
   253→   253→│ Browser (single SPA at /)                                       │
   254→   254→│  └─ Zustand store (session + route)                             │
   255→   255→│  └─ TanStack Query cache (server data)                          │
   256→   256→│  └─ fetch() with Bearer header + cookie                         │
   257→   257→└──────────────────────────┬───────────────────────────────────────┘
   258→   258→                           │
   259→   259→                           ▼
   260→   260→┌────────────────────────────────────────────────────────────────┐
   261→   261→│ Caddy Gateway (:81 → :3000)                                     │
   262→   262→│  └─ 120s timeout (supports long courier API calls)              │
   263→   263→│  └─ ?XTransformPort=PORT for mini-services                      │
   264→   264→└──────────────────────────┬───────────────────────────────────────┘
   265→   265→                           │
   266→   266→                           ▼
   267→   267→┌────────────────────────────────────────────────────────────────┐
   268→   268→│ Next.js 16 App Router                                           │
   269→   269→│  └─ src/app/api/**/route.ts  (170+ API routes)                  │
   270→   270→│  └─ src/app/page.tsx         (single SPA page)                  │
   271→   271→└──────────────────────────┬───────────────────────────────────────┘
   272→   272→                           │ thin wrapper — extracts body, calls action
   273→   273→                           ▼
   274→   274→┌────────────────────────────────────────────────────────────────┐
   275→   275→│ Server Actions  (src/lib/actions/*.ts — 18 files)               │
   276→   276→│  └─ getWorkspace()  →  requirePermission()  →  business logic   │
   277→   277→│  └─ insertAuditLog()  +  insertMetricEvent()  (fire-and-forget) │
   278→   278→└──────────────────────────┬───────────────────────────────────────┘
   279→   279→                           │
   280→   280→                           ▼
   281→   281→┌────────────────────────────────────────────────────────────────┐
   282→   282→│ Prisma Client (src/lib/db.ts — singleton)                       │
   283→   283→│  └─ $queryRaw for atomic sequences + session payload JOIN       │
   284→   284→└──────────────────────────┬───────────────────────────────────────┘
   285→   285→                           │
   286→   286→                           ▼
   287→   287→┌────────────────────────────────────────────────────────────────┐
   288→   288→│ Supabase PostgreSQL  (ap-south-1, session pooler port 5432)     │
   289→   289→└────────────────────────────────────────────────────────────────┘
   290→   290→```
   291→   291→
   292→   292→### 3.2 The five key architectural decisions
   293→   293→
   294→   294→These decisions are NON-NEGOTIABLE — they define FlowOps. Future prompts MUST respect them.
   295→   295→
   296→   296→#### Decision 1: Single SPA route (no per-page routing)
   297→   297→
   298→   298→The entire app lives at `/` (`src/app/page.tsx`). There are no other Next.js pages. Navigation is client-side via Zustand's `navigate(route)` with URL sync via query string (`?view=<route_name>&id=<optional>`).
   299→   299→
   300→   300→**Why**: A single-page architecture keeps all state in one place (Zustand + TanStack Query), eliminates Next.js layout-shift between pages, and lets us code-split aggressively without SSR complications.
   301→   301→
   302→   302→**Consequence**: Every "page" is a route case in a `switch(route.name)` inside `renderRoute()`. There are ~62 named routes in the `AppRoute` discriminated union.
   303→   303→
   304→   304→#### Decision 2: Custom HMAC sessions (NOT NextAuth)
   305→   305→
   306→   306→Sessions are HMAC-signed tokens: `<userId>.<timestamp>.<hmac>`, 30-day TTL. Stored in BOTH:
   307→   307→
   308→   308→1. `localStorage` key `flowops_session_token` (for the API client's Bearer header)
   309→   309→2. HttpOnly cookie `flowops_session` (for fallback when localStorage isn't available, e.g. iframe embeds)
   310→   310→
   311→   311→```typescript
   312→   312→// Session token format
   313→   313→const token = `${userId}.${timestamp}.${hmacSha256(userId + '.' + timestamp, SESSION_SECRET)}`
   314→   314→```
   315→   315→
   316→   316→**Why**: Dual-channel auth works in cross-origin iframes, doesn't require an extra OAuth provider, and avoids the 2.7 MB `next-auth` dependency.
   317→   317→
   318→   318→**Auth flow**:
   319→   319→
   320→   320→```
   321→   321→1. POST /api/auth/login {email, password}
   322→   322→   - Server: verify scrypt(password, user.passwordHash)
   323→   323→   - Server: create session token, set HttpOnly cookie, return token in body
   324→   324→   - Client: store token in localStorage + Zustand store
   325→   325→2. Subsequent requests: client sends Bearer header AND cookie (both)
   326→   326→3. POST /api/auth/logout → clear cookie + localStorage + Zustand
   327→   327→```
   328→   328→
   329→   329→#### Decision 3: Multi-tenant isolation in the APPLICATION layer (not DB RLS)
   330→   330→
   331→   331→There is NO database-level Row-Level Security. Every query scopes by `companyId` in the application code, enforced by `getWorkspace()` + `requirePermission()`.
   332→   332→
   333→   333→**Why**: Prisma's RLS support is limited; managing RLS policies alongside schema changes is error-prone. Application-layer scoping is easier to audit (grep for missing `companyId` filters).
   334→   334→
   335→   335→**Risk**: A bug in `getWorkspace()` or a missing `companyId` filter could leak data across tenants. The audit reports (`INVENTORY_AUDIT.md`, `PRODUCTS_AUDIT.md`, `ORDERS_AUDIT.md`) flagged several instances of missing company-scoping on detail endpoints — these are known tech debt.
   336→   336→
   337→   337→#### Decision 4: Fire-and-forget audit + metric writes
   338→   338→
   339→   339→```typescript
   340→   340→// insertAuditLog + insertMetricEvent return void IMMEDIATELY
   341→   341→// The DB write happens on the event loop AFTER the HTTP response is sent
   342→   342→insertAuditLog({ action: 'order.created', ... })    // no await!
   343→   343→insertMetricEvent({ metricKey: 'order.created', ... })  // no await!
   344→   344→```
   345→   345→
   346→   346→**Why**: Eliminates ~50ms per audit-log write from the request path. Works because FlowOps runs on a long-lived Bun/Node server (NOT serverless), so the event loop survives the HTTP response.
   347→   347→
   348→   348→**Risk**: On a serverless platform (Vercel Edge), these writes would be killed mid-flight. Don't deploy FlowOps to serverless without converting audit logs to a queue + worker pattern.
   349→   349→
   350→   350→#### Decision 5: Adapter pattern for couriers (single integration point)
   351→   351→
   352→   352→Every outbound call to a courier API goes through ONE function: `executeLoggedIntegrationAction()`. This function:
   353→   353→
   354→   354→1. Wraps the call in a try/finally that logs to `IntegrationActionLog` (with request payload + response payload + duration).
   355→   355→2. Re-throws errors after logging.
   356→   356→3. Centralizes retry / timeout behavior (future-proofing).
   357→   357→
   358→   358→```typescript
   359→   359→// Never call adapter methods directly — always through the wrapper:

   370→   370→### 3.3 The request lifecycle (every authenticated API call)
   371→   371→
   372→   372→Every authenticated API route follows the same 6-step pattern. Learn this pattern; every new route should follow it.
   373→   373→
   374→   374→```typescript
   375→   375→// src/app/api/<resource>/route.ts
   376→   376→import { NextRequest } from 'next/server'
   377→   377→import { getWorkspace } from '@/lib/workspace'
   378→   378→import { requirePermission } from '@/lib/workspace'
   379→   379→import { PERMISSIONS } from '@/lib/permissions'
   380→   380→import { insertAuditLog } from '@/lib/audit'
   381→   381→import { handleError } from '@/lib/api-error'
   382→   382→import { readBody } from '@/lib/api-client'
   383→   383→import { createOrderSchema } from '@/lib/validations/order.schemas'
   384→   384→import { createOrder } from '@/lib/actions/order.actions'
   385→   385→
   386→   386→export const runtime = 'nodejs'        // NEVER 'edge' — see §8
   387→   387→export const dynamic = 'force-dynamic' // NEVER statically render
   388→   388→
   389→   389→export async function POST(req: NextRequest) {
   390→   390→  try {
   391→   391→    // 1. Resolve workspace (user + employee + active company)
   392→   392→    //    Uses 60s in-memory cache — see §5
   393→   393→    const ctx = await getWorkspace()
   394→   394→
   395→   395→    // 2. Check permission (throws ApiError 403 if lacking)
   396→   396→    await requirePermission(ctx, PERMISSIONS.ORDERS_CREATE)
   397→   397→
   398→   398→    // 3. Parse + validate body (throws ApiError 400 on invalid)
   399→   399→    const body = await readBody(req)
   400→   400→    const input = createOrderSchema.parse(body)
   401→   401→
   402→   402→    // 4. Call server action (business logic lives here)
   403→   403→    const order = await createOrder(ctx, input)
   404→   404→
   405→   405→    // 5. Fire-and-forget audit + metric writes (no await!)
   406→   406→    insertAuditLog({
   407→   407→      organizationId: ctx.company.organizationId,
   408→   408→      companyId: ctx.company.id,
   409→   409→      employeeId: ctx.employee.id,
   410→   410→      action: 'order.created',
   411→   411→      entityType: 'order',
   412→   412→      entityId: order.id,
   413→   413→    })
   414→   414→
   415→   415→    // 6. Return success response
   416→   416→    return Response.json(order, { status: 201 })
   417→   417→  } catch (err) {
   418→   418→    // handleError converts ApiError(401|403|400|404|500) to proper HTTP status
   419→   419→    return handleError(err)
   420→   420→  }
   421→   421→}
   422→   422→```

   424→   424→### 3.4 The workspace cache system (60-second in-memory cache)
   425→   425→
   426→   426→`getWorkspace()` is called by EVERY authenticated API route. Without caching, that's one Prisma query (~140-280ms to Supabase pooler) per request — a 60% overhead on every API call.
   427→   427→
   428→   428→**Solution**: a per-process in-memory Map cache, 60-second TTL, scoped by `userId`.
   429→   429→
   430→   430→```
   431→   431→┌─────────────────────────────────────────────────────────────────┐
   432→   432→│ src/lib/workspace-cache.ts                                       │
   433→   433→│                                                                  │
   434→   434→│  workspaceCache: Map<userId, { value: WorkspaceContext,          │
   435→   435→│                                expiresAt: number }>              │
   436→   436→│                                                                  │
   437→   437→│  getCachedWorkspace(userId)  → WorkspaceContext | null           │
   438→   438→│  setCachedWorkspace(userId, ctx, ttlMs = 60_000)  → void        │
   439→   439→│  invalidateWorkspaceCache(userId)  → void  (clears role cache too)│
   440→   440→│  clearAllCaches()  → void                                        │
   441→   441→└─────────────────────────────────────────────────────────────────┘
   442→   442→```
   443→   443→
   444→   444→**Cache hit (warm)**:
   445→   445→
   446→   446→```
   447→   447→1. API route calls getWorkspace()
   448→   448→2. getWorkspace() calls getCachedWorkspace(userId) → returns cached ctx
   449→   449→3. Total time: ~0ms (no DB query)
   450→   450→```
   451→   451→
   452→   452→**Cache miss (cold)**:
   453→   453→
   454→   454→```
   455→   455→1. API route calls getWorkspace()
   456→   456→2. getCachedWorkspace(userId) returns null
   457→   457→3. getWorkspace() runs a SINGLE Prisma query that JOINs:
   458→   458→     Profile → settings.activeCompany → Company
   459→   459→            + employees → role
   460→   460→4. setCachedWorkspace(userId, ctx, 60_000) caches the result
   461→   461→5. Total time: ~140-280ms (one DB round-trip)
   462→   462→6. Subsequent calls within 60s hit cache → 0ms
   463→   463→```
   464→   464→
   465→   465→**Cache invalidation** — call `invalidateWorkspaceCache(userId)` when:
   466→   466→
   467→   467→| Trigger | Where called |
   468→   468→|---|---|
   469→   469→| User switches company | `POST /api/workspace/switch` |
   470→   470→| User logs out | `POST /api/auth/logout` (calls `clearAllCaches()`) |
   471→   471→| Admin edits an employee's role | `PATCH /api/employees/[id]` (when role changes) |
   472→   472→| Admin terminates an employee | `POST /api/employees/[id]/terminate` |
   473→   473→| Admin edits a role's permissions | `PATCH /api/roles/[id]` |
   474→   474→
   475→   475→**Multi-instance caveat**: this is a per-process Map, NOT Redis. In a multi-instance deployment, each instance has its own cache. Worst case: a permission change takes 60s to propagate to all instances. Acceptable for an ERP — not for a security-critical system.
   476→   476→
   477→   477→### 3.5 The stock-loss unification system
   478→   478→
   479→   479→Before unification, stock loss was created in **8 disconnected code paths** (Stock Losses module, RTO flow, cycle count, adjust stock, returned-stitched, exchange, supplier return, return scan). This caused:
   480→   480→
   481→   481→- **Double-decrements** — same loss recorded twice (e.g. RTO review + return scan both recorded a damage for the same order item).
   482→   482→- **Missing records** — cycle count and adjust stock decremented `onHand` but created no `StockLossRecord` → Stock Losses dashboard under-reported actual losses.
   483→   483→- **No order linking** — courier-damage losses had no FK back to the order item, so filing courier claims was impossible.
   484→   484→
   485→   485→**Solution**: a single helper `recordStockLoss()` in `src/lib/stock-loss.ts` that every module MUST call.
   486→   486→
   487→   487→```typescript
   488→   488→import { recordStockLoss } from '@/lib/stock-loss'
   489→   489→
   490→   490→const result = await recordStockLoss({
   491→   491→  organizationId, companyId, orgVariantId, locationId,
   492→   492→  lossType: 'damaged',                  // 'damaged' | 'theft' | 'missing' | 'transit_loss' | 'supplier_dispute'
   493→   493→  sourceModule: 'cycle_count',          // discriminator — see table below
   494→   494→  quantity: 2,
   495→   495→  costPerUnit: 500,
   496→   496→  orderItemId: '...',                  // optional — enables dedup
   497→   497→  cycleCountItemId: '...',              // optional — traceability
   498→   498→  employeeId: '...',
   499→   499→  notes: 'Cycle count found 2 damaged',
   500→   500→  // createInventoryTransaction: true (default) — also decrements onHand
   501→   501→})
   502→   502→
   503→   503→if (result.wasDuplicate) {
   504→   504→  // Loss already recorded for this (orderItemId, lossType, sourceModule)
   505→   505→  // — idempotent success, no action needed
   506→   506→}
   507→   507→```
   508→   508→
   509→   509→**The 8 source modules** (the `sourceModule` discriminator):
   510→   510→
   511→   511→| `sourceModule` | Origin code path | Loss types typically recorded |
   512→   512→|---|---|---|
   513→   513→| `stock_loss` | Dedicated Stock Losses module form | damaged, theft, transit_loss |
   514→   514→| `rto` | RTO review queue — `correctReturnItemCondition()` | damaged |
   515→   515→| `cycle_count` | Cycle count approve — theft/unknown shortage | missing |
   516→   516→| `adjust_stock` | Adjust Stock module — negative adjustment | damaged (auto-classified) |
   517→   517→| `returned_stitched` | Returned Stitched module — damaged branch | damaged |
   518→   518→| `supplier_return` | Supplier Returns — status='rejected' branch | supplier_dispute |
   519→   519→| `exchange` | Exchange flow — `verifyOldItemReceived()` damaged | damaged |
   520→   520→| `return_scan` | (planned) Return Order Scan inline damage | damaged |
   521→   521→
   522→   522→**Dedup mechanism**: a partial unique index `stock_loss_orderitem_dedup_idx` on `(orderItemId, lossType, sourceModule) WHERE orderItemId IS NOT NULL`. If a second call attempts to record the same loss, the insert hits the unique constraint → `recordStockLoss()` catches the P2002 error and returns `wasDuplicate: true` (idempotent success).
   523→   523→
   524→   524→**Atomicity**: the loss record + inventory transaction are created in sequence. If the inventory transaction fails, the loss record is deleted (manual rollback). The two writes are NOT in a `db.$transaction` — this is a known tech debt flagged in the audit reports.
   525→   525→
   526→   526→**Known gap**: the `exchange` source module bypasses `recordStockLoss()` in `verifyOldItemReceived()` — it creates the `StockLossRecord` directly without `orderItemId`. This is flagged as a CRITICAL bug in `ORDERS_AUDIT.md` (causes dedup to not apply).

   528→   528→### 3.6 The courier adapter pattern
   529→   529→
   530→   530→FlowOps integrates with three Pakistani couriers via a provider-agnostic adapter interface. The app calls adapters through `getCourierAdapter(providerKey, credentials)` — never instantiates adapter classes directly.
   531→   531→
   532→   532→```
   533→   533→┌──────────────────────────────────────────────────────────────┐
   534→   534→│ src/lib/integrations/registry.ts                              │
   535→   535→│                                                               │
   536→   536→│ COURIER_FACTORIES: Record<providerKey, (creds) => Adapter>    │
   537→   537→│   postex   → new PostExAdapter(creds)                         │
   538→   538→│   leopard  → new LeopardAdapter(creds)                        │
   539→   539→│   tcs      → new TcsAdapter(creds)        ← stub              │
   540→   540→│                                                               │
   541→   541→│ ECOMMERCE_FACTORIES:                                          │
   542→   542→│   shopify  → new ShopifyAdapter(creds)    ← stub              │
   543→   543→│   daraz    → new DarazAdapter(creds)       ← stub              │
   544→   544→└──────────────────────────────────────────────────────────────┘
   545→   545→```
   546→   546→
   547→   547→**The `CourierAdapter` interface** (`src/lib/integrations/types.ts`):
   548→   548→
   549→   549→```typescript
   550→   550→interface CourierAdapter {
   551→   551→  // Required — every courier must implement these:
   552→   552→  bookShipment(input: BookShipmentInput): Promise<{ trackingNumber: string }>
   553→   553→  trackShipment(trackingNumber: string): Promise<ShipmentStatus>
   554→   554→  cancelShipment(trackingNumber: string): Promise<void>
   555→   555→  calculateRate(input: RateInput): Promise<{ rate: number }>          // both stubs today
   556→   556→  parseStatusWebhook(rawPayload: unknown): ParsedWebhook
   557→   557→  verifyWebhookSignature(rawBody, signature, secret): boolean
   558→   558→
   559→   559→  // Optional — capability detection via `'method' in adapter`:
   560→   560→  fetchOperationalCities?(): Promise<City[]>                       // city sync
   561→   561→  createPickupAddress?(input: PickupAddressInput): Promise<{ id: string }>
   562→   562→  fetchExistingPickupAddresses?(): Promise<PickupAddress[]>
   563→   563→  trackBulkShipments?(trackingNumbers: string[]): Promise<ShipmentStatus[]>  // PostEx only
   564→   564→  generateLoadSheet?(trackingNumbers: string[], pickupAddress?): Promise<{ pdfUrl: string }>  // PostEx only
   565→   565→  pingConnection?(): Promise<boolean>
   566→   566→}
   567→   567→```
   568→   568→
   569→   569→**Adapter implementation status** (from `COURIER_ADAPTER_STATUS` map in `registry.ts`):
   570→   570→
   571→   571→| Provider | Status | Notes |
   572→   572→|---|---|---|
   573→   573→| `postex` | **live** | Full implementation — booking, single + bulk tracking (with 400 fallback), cities, pickup addresses, load sheets, cancellation |
   574→   574→| `leopard` | **live** | Full implementation — booking, tracking, cities (with shipmentTypes), createShipper, cancellation. No webhook HMAC signature — security via `webhookEndpointId` URL routing |
   575→   575→| `tcs` | `framework_ready` | Stub — methods throw `not implemented`. Ready for future integration |
   576→   576→| `shopify` | `framework_ready` | Stub — `createOrderFromShopifyWebhook()` is fully implemented (parses payload, matches customer, creates order), but the adapter that maps Shopify webhook payloads is a stub |
   577→   577→| `daraz` | `framework_ready` | Stub — no order creation path |
   578→   578→
   579→   579→**Every outbound call is logged** — `executeLoggedIntegrationAction()` wraps the adapter call and writes to `IntegrationActionLog` with:
   580→   580→
   581→   581→| Field | Description |
   582→   582→|---|---|
   583→   583→| `actionType` | `book_shipment`, `cancel_shipment`, `track_shipment`, `track_shipment_bulk`, `generate_load_sheet`, `create_pickup_address`, etc. |
   584→   584→| `direction` | `outbound` (always for these calls) |
   585→   585→| `requestPayload` | The actual business data sent to the courier (city, address, COD amount, tracking number) — NEW, was always null before Aug 2026 |
   586→   586→| `responsePayload` | The courier's response (success or error body) |
   587→   587→| `durationMs` | End-to-end wall-clock time |
   588→   588→| `success` | `true` if the adapter returned without throwing |
   589→   589→| `error` | Error message if `success=false` |
   590→   590→
   591→   591→**No credentials are logged** — only business data. Credentials live in `CompanyIntegration.encryptedCredentials` (AES-256-GCM via `INTEGRATION_ENCRYPTION_KEY`).

   593→   593→### 3.7 Background jobs
   594→   594→
   595→   595→FlowOps runs on a long-lived Bun server, so Vercel-style cron (`vercel.json`) does NOT fire. Two background jobs are started in-process via Next.js's `instrumentation.ts` hook:
   596→   596→
   597→   597→| Job | Interval | Purpose | Env var to disable |
   598→   598→|---|---|---|---|
   599→   599→| PostEx status poller | 30 minutes | Polls all active orders with tracking numbers; transitions dispatched → delivered / returned / cancelled | `ENABLE_IN_PROCESS_POLLER=false` |
   600→   600→| Exchange-rate refresh | 24 hours | Fetches daily FX rates relative to USD; stores in `ExchangeRateSnapshot` | `ENABLE_IN_PROCESS_FX_REFRESH=false` |
   601→   601→
   602→   602→The other 3 cron jobs defined in `vercel.json` (city sync every 3h, scan reports daily 1AM, Leopard safety-net every 12h) require **manual triggering or external scheduler** (cron-job.org, GitHub Actions). They are exposed at `/api/cron/*` and accept GET (manual) + POST with `x-cron-secret` header.

   604→   604→### 3.8 The frontend routing architecture
   605→   605→
   606→   606→```
   607→   607→src/app/page.tsx
   608→   608→  ├─ useQuery(['session', 'me']) → GET /api/auth/me
   609→   609→  │    (refetchOnWindowFocus: true — catches terminated-employee state)
   610→   610→  ├─ if !hydrated → <Loader2 spin /> loading screen
   611→   611→  ├─ if !user → <AuthShell>{login|register|forgot|reset}</AuthShell>
   612→   612→  ├─ if user && !isOnboarded → <OnboardingView />
   613→   613→  └─ if user && isOnboarded → <DashboardShell>{renderRoute(route)}</DashboardShell>
   614→   614→```
   615→   615→
   616→   616→`renderRoute(route)` is a `switch(route.name)` over the ~62 named routes in the `AppRoute` discriminated union. Every view component is lazy-loaded via `next/dynamic` with `ssr: false`:
   617→   617→
   618→   618→```typescript
   619→   619→const ProductsView = dynamic(
   620→   620→  () => import('@/components/products/products-view').then(m => ({ default: m.ProductsView })),
   621→   621→  { ssr: false, loading: LoadingFallback }
   622→   622→)
   623→   623→```
   624→   624→
   625→   625→This code-split the bundle from 1 monolithic 3,148 KB chunk to 95 chunks (5 root + 90 lazy), reducing First Load JS to 1,070 KB (66% reduction).
   626→   626→
   627→   627→**IMPORTANT**: do NOT add module-scope `() => import(...)` maps (a previous attempt called `ROUTE_CHUNK_LOADERS` caused Turbopack to create 55 duplicate chunks, +1,303 KB). Each route's code should be imported ONLY in its `dynamic()` call.

   768→   768→## 5. Key Systems
   769→   769→
   770→   770→These are the cross-cutting systems that span multiple modules. Understanding these is essential before touching inventory, orders, or stock-loss code.
   771→   771→
   772→   772→### 5.1 Stock types (onHand / reserved / available / incoming)
   773→   773→
   774→   774→Every variant × location pair has 4 stock numbers in `InventoryPool`:
   775→   775→
   776→   776→| Field | DB column | What it means | Mutated by |
   777→   777→|---|---|---|---|
   778→   778→| **onHand** | `onHand Int @default(0)` | Physical units currently in the warehouse | `purchase_received` (+), `sale_dispatched` (−), `return_resellable` (+), `transfer_in` (+), `transfer_out` (−), `damage_writeoff` (−), etc. |
   779→   779→| **reserved** | `reserved Int @default(0)` | Units reserved for confirmed orders (not yet dispatched) | `order_reserved` (+), `order_unreserved` (−), `sale_dispatched` (−) |
   780→   780→| **incoming** | `incoming Int @default(0)` | Units on order from supplier (PO confirmed, not yet received) | PO confirm (+), PO receive (−, moves to onHand), PO cancel (−) |
   781→   781→| **available** | (computed, no DB column) | `onHand - reserved` — what's actually sellable | Computed in app code every time it's needed |
   782→   782→
   783→   783→**The invariant** — at any moment, for any pool:
   784→   784→```
   785→   785→onHand >= reserved           (you can't reserve more than you physically have)
   786→   786→available = onHand - reserved (computed; never stored)
   787→   787→incoming >= 0                (can't have negative incoming)
   788→   788→```
   789→   789→
   790→   790→`processInventoryTransaction()` enforces these invariants — it validates before mutating and throws on violation. **NEVER** mutate `InventoryPool` directly with `db.inventoryPool.update()` — always go through `processInventoryTransaction()`.
   791→   791→
   792→   792→### 5.2 Order lifecycle (create → confirm → cancel/un-cancel → dispatch → RTO → return)
   793→   793→
   794→   794→The order lifecycle is the heart of FlowOps. Every transition has inventory side-effects.
   795→   795→
   796→   796→```
   797→   797→                              ┌─────────── cancel (unreserve) ─────────┐
   798→   798→                              │                                         │
   799→   799→                              ▼                                         │
   800→   800→   pending ──────────► confirmed ──► processing ──► packed ──► dispatched ──► delivered
   801→   801→       │                   │                                         │
   802→   802→       │                   │ unreserve + cancel                       │
   803→   803→       │                   ▼                                         ▼
   804→   804→       └──────────────► cancelled                              returned
   805→   805→                           ▲                                  (RTO → restock)
   806→   806→                           │
   807→   807→                   partially_backordered
   808→   808→                           │
   809→   809→                           ▼ (when stock arrives, auto-fulfills)
   810→   810→                       confirmed
   811→   811→```
   812→   812→
   813→   813→**Transition rules**:
   814→   814→
   815→   815→| Transition | Trigger | Inventory effect | Reverse-able? |
   816→   816→|---|---|---|---|
   817→   817→| `pending → confirmed` | Manual confirm OR auto-confirm (if prepaid OR `requireOrderConfirmation=false`) | `reserveStockForOrder()` per line item | Yes — `confirmed → cancelled` |
   818→   818→| `pending → cancelled` | Manual cancel | None (nothing reserved) | ❌ No un-cancel — must recreate |
   819→   819→| `confirmed → partially_backordered` | When reservation fails for some items | Reserve available; backorder remainder | Yes — auto-fulfills when stock arrives |
   820→   820→| `confirmed → processing` | Manual mark processing (or `mark_packed` scan mode) | None | Yes |
   821→   821→| `processing → packed` | Manual mark packed (or `mark_packed` scan) | None | Yes |
   822→   822→| `confirmed/processing/packed → dispatched` | Manual dispatch (or auto from PostEx/Leopard poll: `picked_up` triggers dispatch) | `dispatchOrder()` → `sale_dispatched` (decreases onHand + reserved) | ❌ No un-dispatch |
   823→   823→| `dispatched → delivered` | Manual mark delivered (or auto from courier poll: `delivered` status) | None | Yes |
   824→   824→| `dispatched → returned` (RTO) | Manual RTO mark (or auto from courier poll: `returned` status) | `restockOrderForRto()` → `return_resellable` or `return_stitched_received` (increases onHand) | Yes |
   825→   825→| `dispatched → cancelled` | ❌ BLOCKED — post-dispatch cancellation not allowed | — | — |
   826→   826→| `confirmed → cancelled` (with courier booking) | Manual cancel | `cancelCourierBooking()` first (pre-pickup only), then `unreserveStockForOrder()` | ❌ No un-cancel |
   827→   827→
   828→   828→**Payment types** (separate from order status):
   829→   829→
   830→   830→| `paymentType` | Description | `paymentStatus` flow |
   831→   831→|---|---|---|
   832→   832→| `full_cod` | Cash on delivery — full amount collected by courier | `cod_pending` → `cod_collected` (on delivery) |
   833→   833→| `partial_advance` | Partial advance paid online, remainder COD | `cod_pending` → `advance_paid` → `cod_collected` |
   834→   834→| `fully_prepaid` | Full amount paid online before dispatch | `cod_pending` → `fully_prepaid` → `advance_paid` (on dispatch) |
   835→   835→
   836→   836→**Auto-confirm rule**: if `paymentType === 'fully_prepaid'` OR `requireOrderConfirmation === false`, the order auto-confirms on creation (skips the Pending Confirmation queue).
   837→   837→
   838→   838→**Auto-book rule**: if `courierBookingMode === 'automatic'`, order confirmation fires `maybeAutoBookOrder()` in the background (PostEx can take 50-100s). The booker is fire-and-forget — order creation response doesn't wait.
   839→   839→

   841→   841→
   842→   842→**Single booking** — `bookOrderWithCourier()` in `src/lib/actions/booking.actions.ts` (969 lines). This is the single source of truth — used by both Booking Workbench (manual) and `maybeAutoBookOrder()` (automatic).

   845→   845→// Simplified flow:
   846→   846→const result = await bookOrderWithCourier({
   847→   847→  orderId,
   848→   848→  ctx,                    // workspace context (for permission check)
   849→   849→  skipCourierCall: false, // true = only update internal state (used by cancel-after-book)

   851→   851→
   852→   852→// What it does:
   853→   853→// 1. Resolve courier adapter (from CompanyIntegration for the order's courier)
   854→   854→// 2. Validate city (revalidateCityAtBookingTime — 3h staleness guard + live fallback)
   855→   855→// 3. Build BookShipmentInput (customer info, address, COD amount, items)

   899→   899→### 5.5 Atomic number generation (`get_next_sequence_number()`)
   900→   900→
   901→   901→FlowOps generates human-readable numbers for orders, POs, self-fulfilled references, exchange shipments, and drafts. Format: `<PREFIX>-<YEAR>-<SEQ>` (e.g. `ORD-2026-00123`, `PO-2026-00045`, `SF-2026-00001`, `EXCH-2026-00012`).
   902→   902→
   903→   903→**Problem**: the legacy `generate_order_number()` SQL function (migration 001) used `SELECT MAX(...) + 1` — a classic race condition under concurrent inserts. Two simultaneous order creates could grab the same MAX+1, and the `@@unique([companyId, flowopsOrderNumber])` constraint would reject the second with Prisma P2002 → 500 error to the user.
   904→   904→
   905→   905→**Solution**: migration 026 (`supabase/migrations/026_atomic_sequence_counter.sql`) introduced `get_next_sequence_number(p_org_id, p_type, p_year)` — an atomic `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` function.
   906→   906→
   907→   907→```sql
   908→   908→CREATE TABLE IF NOT EXISTS "number_sequences" (
   909→   909→  "organizationId" TEXT NOT NULL,
   910→   910→  "type"            TEXT NOT NULL,    -- 'order_number' | 'po_number' | 'sf_number' | 'exchange_shipment_number' | 'draft_number'
   911→   911→  "year"            INT  NOT NULL,
   912→   912→  "nextNumber"      INT  NOT NULL DEFAULT 1,
   913→   913→  CONSTRAINT "number_sequences_org_type_year_key" UNIQUE ("organizationId", "type", "year")
   914→   914→);
   915→   915→
   916→   916→CREATE OR REPLACE FUNCTION get_next_sequence_number(
   917→   917→  p_org_id TEXT, p_type TEXT, p_year INT
   918→   918→) RETURNS INT AS $$
   919→   919→  INSERT INTO "number_sequences" ("organizationId", "type", "year", "nextNumber")
   920→   920→  VALUES (p_org_id, p_type, p_year, 1)
   921→   921→  ON CONFLICT ("organizationId", "type", "year")
   922→   922→  DO UPDATE SET "nextNumber" = "number_sequences"."nextNumber" + 1
   923→   923→  RETURNING "number_sequences"."nextNumber";
   924→   924→$$ LANGUAGE sql;
   925→   925→```
   926→   926→
   927→   927→**Usage** (verified in source code as of this rewrite):
   928→   928→
   929→   929→| Generator | Where | Sequence type | Status |
   930→   930→|---|---|---|---|
   931→   931→| `generateOrderNumber(companyId)` | `src/lib/actions/order.actions.ts` line ~90 | `'order_number'` | ✅ Uses `get_next_sequence_number()` |
   932→   932→| `generateSelfFulfilledReference(companyId)` | `src/lib/actions/order.actions.ts` line ~128 | `'sf_number'` | ✅ Uses `get_next_sequence_number()` |
   933→   933→| `generatePoNumber(orgId)` | `src/lib/inventory.ts` line ~455 | `'po_number'` | ✅ Uses `get_next_sequence_number()` |
   934→   934→| `generateExchangeShipmentNumber()` | (legacy SQL function from migration 008) | `'exchange_shipment_number'` | ⚠️ Still uses legacy MAX-based sequence (global, not per-org). Known tech debt. |
   935→   935→| `generateDraftNumber()` | (legacy SQL function from migration 006) | `'draft_number'` | ⚠️ Still uses legacy MAX-based sequence. Known tech debt. |
   936→   936→
   937→   937→**Migrating the legacy generators**: write a migration that wraps `generate_exchange_shipment_number()` and `generate_draft_number()` to call `get_next_sequence_number()` internally. The function signatures stay the same; the implementation becomes atomic.

   956→   956→**Two-tier permission model**:
   957→   957→
   958→   958→| Tier | Who | How permissions checked |
   959→   959→|---|---|---|
   960→   960→| **Elevated** | Owner, Founder, Co-Founder, Investor (`systemRoleKey` ∈ these values) | Bypass ALL permission checks via `isElevated()` — always returns `true` |
   961→   961→| **Standard** | All other roles (custom roles created per-company) | Check `employee.permissions.includes(key)` — explicit grant required |
   962→   962→
   963→   963→**`requirePermission(ctx, key)`** in `src/lib/workspace.ts`:
   964→   964→
   965→   965→```typescript
   966→   966→export async function requirePermission(
   967→   967→  ctx: WorkspaceContext,
   968→   968→  key: string,
   969→   969→): Promise<void> {
   970→   970→  // Elevated roles bypass all checks
   971→   971→  if (ctx.employee.role.roleTier === 'elevated') return
   972→   972→
   973→   973→  // Fast path: check cached permission set (0ms)
   974→   974→  const cached = getCachedRolePermissions(ctx.employee.roleId)
   975→   975→  if (cached) {
   976→   976→    if (cached.has(key)) return
   977→   977→    throw new ApiError(403, `You lack permission: ${key}`)
   978→   978→  }
   979→   979→
   980→   980→  // Cache miss: fetch role's permissions from DB
   981→   981→  const perms = await db.rolePermission.findMany({
   982→   982→    where: { roleId: ctx.employee.roleId },
   983→   983→    select: { permissionKey: true },
   984→   984→  })
   985→   985→  const set = new Set(perms.map((p) => p.permissionKey))
   986→   986→  setCachedRolePermissions(ctx.employee.roleId, set)  // 60s TTL
   987→   987→
   988→   988→  if (set.has(key)) return
   989→   989→  throw new ApiError(403, `You lack permission: ${key}`)
   990→   990→}
   991→   991→```
   992→   992→
   993→   993→**Frontend equivalent**: `useCan()` hook returns a function `(key: string) => boolean`. Elevated roles always return `true`. Standard roles check the cached `employee.permissions` array.
   994→   994→
   995→   995→**`ordersDataScope`** — a per-role toggle that controls whether the role sees all orders in the company or only their own. Used by `resolveOrderScope()` in `src/lib/order-scope.ts` (modern pattern used by all queue routes).
   996→   996→
   997→   997→### 5.7 Workspace cache (60-second in-memory cache for `getWorkspace()`)
   998→   998→
   999→   999→See §3.4 for the full design. The short version:
  1000→  1000→
  1001→  1001→| Function | Purpose |
  1002→  1002→|---|---|
  1003→  1003→| `getCachedWorkspace(userId)` | Returns cached `WorkspaceContext` if not expired, else `null` |
  1004→  1004→| `setCachedWorkspace(userId, ctx, ttlMs = 60_000)` | Caches the workspace for 60s |
  1005→  1005→| `invalidateWorkspaceCache(userId)` | Clears the user's workspace + ALL role permission caches (because if the user's role changed, we don't know the old roleId without a DB query) |
  1006→  1006→| `clearAllCaches()` | Nuclear option — clears everything. Used on logout. |
  1007→  1007→
  1008→  1008→**Role permissions cache** — separate cache, also 60s TTL, keyed by `roleId`. Eliminates the per-permission-check DB query. Cleared whenever the workspace cache is invalidated (because role changes are correlated).
  1009→  1009→
  1010→  1010→**When to call `invalidateWorkspaceCache(userId)`**:
  1011→  1011→
  1012→  1012→| Event | Where to call |
  1013→  1013→|---|---|
  1014→  1014→| User switches active company | `POST /api/workspace/switch` route |
  1015→  1015→| User logs out | `POST /api/auth/logout` route |
  1016→  1016→| Admin edits an employee's role | `PATCH /api/employees/[id]` route (when role changes) |
  1017→  1017→| Admin terminates an employee | `POST /api/employees/[id]/terminate` route |
  1018→  1018→| Admin edits a role's permissions | `PATCH /api/roles/[id]` route |
  1019→  1019→
  1020→  1020→**Multi-instance caveat**: this is a per-process Map. In a multi-replica deployment, each instance has its own cache. Worst case: a permission change takes 60s to propagate to all instances. Acceptable for an ERP — revisit when adding a second replica.

  1369→  1369→### 8.5 Other operational gotchas
  1370→  1370→
  1371→  1371→#### Environment
  1372→  1372→
  1373→  1373→1. **`.env` reverts to SQLite on sandbox restart** — the `predev` script guards against this. Always verify before starting.
  1374→  1374→2. **DB latency from sandbox** — Mumbai region (~100ms per query). Performance optimizations (fire-and-forget, parallel queries, single-JOIN getWorkspace, 60s workspace cache) have been applied.
  1375→  1375→3. **Turbopack instability** — dev server can hang during compilation in the sandbox (memory issue). Clear `.next/` cache and restart.
  1376→  1376→4. **Hydration mismatch from browser extensions** — Grammarly injects `data-gr-ext-installed` + `data-new-gr-c-s-check-loaded` attributes into `<body>`. Fixed via `suppressHydrationWarning` on `<body>` in `layout.tsx`. If new hydration errors appear, check for other browser-extension-injected attributes.
  1377→  1377→
  1378→  1378→#### Bundling
  1379→  1379→
  1380→  1380→5. **Do NOT add module-scope `import()` maps** — a `ROUTE_CHUNK_LOADERS` map with 55 `() => import(...)` entries caused Turbopack to create 55 duplicate chunks (+1,303 KB). The ONLY place each route's code should be imported is the `dynamic()` call in `page.tsx`. See §3.8 warning.
  1381→  1381→
  1382→  1382→#### Integrations
  1383→  1383→
  1384→  1384→6. **PostEx bulk tracking API** — intermittently returns HTTP 400 "Required List parameter 'TrackingNumbers' is not present". Handled with single-track fallback. Don't "fix" by removing the bulk path — single-track is too slow for 100+ orders.
  1385→  1385→7. **Vercel cron doesn't fire** — on long-lived server. In-process pollers added for PostEx (30min) + exchange rate refresh (24h). Other crons (city sync, scan reports, Leopard safety-net) need manual triggering or external scheduler. The `ENABLE_IN_PROCESS_POLLER` + `ENABLE_IN_PROCESS_FX_REFRESH` env vars (default `true`) can disable for multi-replica deployments.
  1386→  1386→8. **PostEx API lag** — parcels may be physically picked up but PostEx's API still shows "Booked" for hours. This is a PostEx issue, not FlowOps.
  1387→  1387→
  1388→  1388→#### Schema
  1389→  1389→
  1390→  1390→9. **SQL functions must be applied manually** — `generate_order_number()`, `generate_self_fulfilled_reference()`, `normalize_phone()`, `match_or_create_customer()`, `get_next_sequence_number()`, etc. are NOT in the Prisma schema. They must be applied via raw SQL to the DB. A consolidated file `supabase/functions-only.sql` contains all 24+ functions + 2 sequences + 12 triggers + 2 partial unique indexes (`invitation_pending_email_unique` + `market_one_default_per_company` + `stock_loss_orderitem_dedup_idx`).
  1391→  1391→10. **No DB-level RLS** — all multi-tenant isolation is in the app layer. A bug in `getWorkspace()` or a missing `companyId` filter could leak data across tenants.
  1392→  1392→11. **No `available` column** — `available = onHand - reserved` is computed in app code every time it's needed.
  1393→  1393→12. **Order-create child components are module-level functions** — `CustomerSection`, `ItemsSection`, `PaymentSection`, etc. in `order-create-view.tsx` are declared at the module level (NOT closures inside `OrderCreateView`). Any new state variable used in these child components MUST be passed as a prop — referencing it directly will compile fine but crash at runtime with `ReferenceError`. TypeScript does NOT catch this. When adding new state/hooks to `OrderCreateView` that child components need, always: (1) add it to the child's destructured props, (2) add it to the child's type definition, (3) pass it from `<OrderCreateView>` to `<ChildComponent>`.
  1394→  1394→
  1395→  1395→#### Performance
  1396→  1396→
  1397→  1397→13. **Audit/metric writes are fire-and-forget** — on a serverless platform (Vercel Edge), these would be killed mid-flight. The current long-lived Bun server keeps them alive.
  1398→  1398→14. **`executeLoggedIntegrationAction` has a blocking DB write** — the `IntegrationActionLog` insert in the `finally` block is awaited (~150ms per booking). Not yet converted to fire-and-forget.
  1399→  1399→15. **`/api/auth/me` performance** — FIXED. `buildSessionPayload()` now uses a single raw SQL JOIN. Latency reduced from ~696ms to ~210ms warm (67% faster). Server-side in-memory cache deliberately deferred after the raw-SQL JOIN fix brought warm requests to ~210ms — revisit when adding a second replica or when concurrent DB read load becomes measurable.
