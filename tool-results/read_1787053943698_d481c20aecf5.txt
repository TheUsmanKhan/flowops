    37→    37→## 1. Executive Summary
    38→    38→
    39→    39→**FlowOps** is a multi-tenant SaaS ERP built for Pakistani e-commerce businesses. It manages the complete order lifecycle: product catalog → customer management → order creation → inventory reservation → courier booking → dispatch → delivery/RTO → returns/exchanges. It integrates with Pakistani courier services (PostEx, Leopard) for real-time booking and status tracking.
    40→    40→
    41→    41→**Core value proposition**: One system to manage products, inventory, orders, customers, and courier bookings — replacing the spreadsheets + WhatsApp + manual courier portal workflow that Pakistani e-commerce sellers currently use.
    42→    42→
    43→    43→**Scale**: 58 Prisma models, 148 API routes, ~153 React components (101 non-UI + 52 shadcn/ui), 21 SQL migrations, 30 permission keys, 2 live courier integrations.
    44→    44→
    45→    45→**Performance posture** (as of latest optimization pass):
    46→    46→- First Load JS: **1,070 KB** (down from 3,148 KB baseline — 66% reduction via code-splitting)
    47→    47→- Total JS across all chunks: **4,665 KB** (95 chunks — was 10 chunks pre-split)
    48→    48→- All 70 data-fetching views use TanStack Query (was 64/70 — 6 migrated from raw `useEffect`+`api.get()`)
    49→    49→- `React.memo` used on leaf components in 6 largest views
    50→    50→- 10 dead dependencies removed (node_modules: 1.2 GB, was 1.3 GB)
    51→    51→- Route-aware `LoadingFallback` renders PageHeader text immediately at Suspense boundary

    55→    55→## 2. What FlowOps Is
    56→    56→
    57→    57→### Target User
    58→    58→Pakistani e-commerce sellers (Instagram/Facebook/Daraz/Shopify) who:
    59→    59→- Sell products COD (Cash on Delivery) — the dominant payment method in Pakistan
    60→    60→- Ship via local couriers (PostEx, Leopard, TCS)
    61→    61→- Need to track which orders are confirmed, packed, dispatched, delivered, or returned (RTO)
    62→    62→- Need inventory management (stock-based + made-to-order)
    63→    63→- Need customer management with RTO-rate flagging (high-return customers)
    64→    64→
    65→    65→### Multi-Tenant Model
    66→    66→```
    67→    67→Organization (top-level tenant, owned by one user)
    68→    68→  └── Company (sub-tenant — a brand/store under the org)
    69→    69→        ├── Employees (users with roles/permissions in this company)
    70→    70→        ├── Products (company subscribes to org-level product templates)
    71→    71→        ├── Inventory (company-owned stock in locations)
    72→    72→        ├── Orders (company's orders)
    73→    73→        ├── Customers (org-level, shared across companies in the org)
    74→    74→        └── Integrations (company's courier connections)
    75→    75→```
    76→    76→
    77→    77→A user can belong to multiple companies (via Employee records) and switch between them using the workspace switcher. The active company is stored in `UserSetting.activeCompanyId`.
    78→    78→
    79→    79→### Order Lifecycle (the heart of the system)
    80→    80→```
    81→    81→pending → confirmed → processing → packed → dispatched → delivered
    82→    82→                ↓                                      ↓
    83→    83→         partially_backordered                       rto
    84→    84→                ↓
    85→    85→            cancelled
    86→    86→```
    87→    87→
    88→    88→Every transition has inventory side-effects:
    89→    89→- **Confirm**: reserve stock (`reserved += qty`) or backorder if insufficient
    90→    90→- **Dispatch**: deduct stock (`onHand -= qty`, `reserved -= qty`)
    91→    91→- **Cancel**: unreserve stock (`reserved -= qty`)
    92→    92→- **RTO**: restock (`onHand += qty` via `return_resellable` or `return_stitched_received`)

   161→   161→## 4. Architecture Overview
   162→   162→
   163→   163→### High-Level Data Flow
   164→   164→```
   165→   165→Browser (SPA at /)
   166→   166→  ↓ Authorization: Bearer <token> + cookie
   167→   167→Caddy Gateway (:81 → :3000)
   168→   168→  ↓
   169→   169→Next.js 16 API Routes (148 routes under src/app/api/)
   170→   170→  ↓
   171→   171→Server Actions (src/lib/actions/*.ts)
   172→   172→  ↓
   173→   173→Prisma Client (src/lib/db.ts)
   174→   174→  ↓
   175→   175→Supabase PostgreSQL (Mumbai)
   176→   176→```
   177→   177→
   178→   178→### Key Architectural Decisions
   179→   179→
   180→   180→1. **Single SPA route** — the entire app lives at `/` (`src/app/page.tsx`). Navigation is client-side via Zustand's `navigate(route)` with URL sync. There are no other Next.js pages.
   181→   181→
   182→   182→2. **Custom HMAC sessions** — Sessions are HMAC-signed tokens: `userId.timestamp.hmac` (30-day TTL). Dual-channel: `Authorization: Bearer` header (works in iframes/cross-origin) + HttpOnly cookie fallback. (`next-auth` was previously installed but unused; it was removed in Step 4 — see §3.)
   183→   183→
   184→   184→3. **Multi-tenant isolation in app layer** — `getWorkspace()` in `src/lib/workspace.ts` resolves the caller's active company from `UserSetting.activeCompanyId` via a SINGLE Prisma JOIN query (Profile → settings.activeCompany + employees.role). No database-level RLS — all scoping is enforced in the application layer via `requirePermission()`.
   185→   185→
   186→   186→4. **Fire-and-forget audit/metric writes** — `insertAuditLog()` and `insertMetricEvent()` return `void` immediately (detached promises via `fireAndForget()`). This works because the app runs on a long-lived Bun/Node server where the event loop survives the HTTP response.
   187→   187→
   188→   188→5. **Adapter pattern for couriers** — provider-agnostic `CourierAdapter` interface. Only PostEx + Leopard are real implementations; TCS is a stub. All courier calls go through `executeLoggedIntegrationAction()` which logs every API call to `integration_action_logs`.
   189→   189→
   190→   190→6. **Prisma `db push` workflow** — the `supabase/migrations/*.sql` files are reference SQL. The live schema is managed via `prisma db push` against `prisma/schema.prisma`. SQL functions (like `generate_order_number()`) must be applied manually to the DB.

   334→   334→## 6. Authentication & Multi-Tenancy
   335→   335→
   336→   336→### Session System
   337→   337→- **Token format**: `userId.timestamp.hmac` (HMAC-SHA256 signed)
   338→   338→- **TTL**: 30 days
   339→   339→- **Storage**: `localStorage` key `flowops_session_token` + HttpOnly cookie `flowops_session`
   340→   340→- **Dual-channel**: API client sends BOTH `Authorization: Bearer <token>` header AND cookie — works in iframes, cross-origin, and same-origin
   341→   341→
   342→   342→### Auth Flow
   343→   343→```
   344→   344→1. POST /api/auth/login {email, password}
   345→   345→2. Server: verify scrypt hash → create session token → set cookie + return token
   346→   346→3. Client: store token in localStorage + Zustand store
   347→   347→4. Subsequent requests: send Bearer token + cookie
   348→   348→5. POST /api/auth/logout → clear cookie + localStorage
   349→   349→```

   368→   368→### Workspace Resolution
   369→   369→`getWorkspace()` in `src/lib/workspace.ts`:
   370→   370→- Resolves caller's active company + employee + role in a SINGLE Prisma query (Profile → settings.activeCompany + employees.role)

   372→   372→- Returns `WorkspaceContext` = `{ user, employee, company }`
   373→   373→- Called by nearly every authenticated API route

  1019→  1019→## 11. Frontend Architecture
  1020→  1020→
  1021→  1021→### 11.1 Single-Page App Structure
  1022→  1022→
  1023→  1023→The entire app is a **single Next.js page** at `/` (`src/app/page.tsx`). All "pages" are route cases inside a `switch(route.name)` in `renderRoute()`.
  1024→  1024→
  1025→  1025→**Code-splitting strategy** (Step 1 optimization — August 2026):
  1026→  1026→All 70+ view components are lazy-loaded via `next/dynamic` with `ssr: false`:
  1027→  1027→```typescript
  1028→  1028→const ProductsView = dynamic(
  1029→  1029→  () => import('@/components/products/products-view').then(m => ({ default: m.ProductsView })),
  1030→  1030→  { ssr: false, loading: LoadingFallback }
  1031→  1031→)
  1032→  1032→```
  1033→  1033→This splits the bundle into ~95 chunks: 5 root main (always loaded) + 90 lazy chunks (loaded on-demand when the user navigates to that route). First Load JS dropped from 3,148 KB → 1,070 KB (66% reduction).
  1034→  1034→
  1035→  1035→**Route-aware LoadingFallback** (renders PageHeader text immediately at Suspense boundary):
  1036→  1036→```typescript
  1037→  1037→const ROUTE_METADATA: Record<string, { title: string; description?: string }> = {
  1038→  1038→  products: { title: 'Products', description: 'Manage your product catalog...' },
  1039→  1039→  // ... 55 routes total
  1040→  1040→}
  1041→  1041→const LoadingFallback = () => {
  1042→  1042→  const route = useAppStore((s) => s.route)
  1043→  1043→  const meta = ROUTE_METADATA[route.name]
  1044→  1044→  // Renders PageHeader + skeleton grid — LCP text paints immediately
  1045→  1045→}
  1046→  1046→```
  1047→  1047→This makes the LCP text element paint as soon as the Suspense boundary renders, NOT after the lazy chunk downloads.
  1048→  1048→
  1049→  1049→> ⚠️ **IMPORTANT — Do NOT add `ROUTE_CHUNK_LOADERS`**: A previous attempt to "prefetch" route chunks in parallel with session hydration used a module-scope map of 55 `() => import(...)` functions. Turbopack statically analyzed all 55 targets and created DUPLICATE chunks (+55 chunks, +1,303 KB). This was removed. The ONLY place each route's code should be imported is the `dynamic()` call. Do not reintroduce module-scope import maps.
  1050→  1050→
  1051→  1051→**Pre-switch gating logic:**
  1052→  1052→1. **Hydration via TanStack Query**: On mount, `useQuery(['session', 'me'])` fires `GET /api/auth/me`. This query has a **deliberate per-query override**: `refetchOnWindowFocus: true` (the global default is `false`). Session validity (active employee status, permissions, platform-level access) is the one place where catching a change quickly after the user returns to a background tab matters — e.g., an employee terminated while their tab sat in the background should see their UI reflect that promptly on refocus. Every other view stays on the global `false` default because they display data, not gate security-sensitive UI. The query result is wired into `useAppStore.setSession()` via a `useEffect` — first fetch shows a loading spinner, background refetches update the store silently (only if data changed). If URL has `?view=...`, restores that route. Listens to `popstate` for browser back/forward.
  1053→  1053→2. **Loading screen**: `<Loader2 className="animate-spin">` while `!hydrated` (first session fetch only — background refetches do NOT show a spinner).
  1054→  1054→3. **Unauthenticated** (`!user`): login/register/forgot/reset forms, all wrapped in `AuthShell`.
  1055→  1055→4. **Authenticated but not onboarded**: `OnboardingView` / `CreateOrganizationView` / `CreateCompanyView`.
  1056→  1056→5. **Authenticated + onboarded**: `<DashboardShell>{renderRoute(route)}</DashboardShell>`.

  1092→  1092→### 11.3 URL Sync (`src/lib/routing/url-sync.ts`)
  1093→  1093→
  1094→  1094→**Strategy**: Query-string navigation. Routes are encoded as URL query params: `/?view=<route_name>&id=<optional>&token=<optional>`.
  1095→  1095→

  1105→  1105→### 11.4 API Client (`src/lib/api-client.ts`)
  1106→  1106→
  1107→  1107→- **Token storage**: `localStorage` key `'flowops_session_token'`
  1108→  1108→- **Request flow**: `fetch(url, { credentials: 'include', cache: 'no-store', headers: { Authorization: Bearer <token> } })`
  1109→  1109→- **Dual-channel auth**: Bearer header (works in iframes/cross-origin) + cookie fallback
  1110→  1110→- **Error handling**: Throws `FetchError(status, message)` on non-2xx, reads `body.error` for server message
  1111→  1111→- **Exports**: `api.get/post/put/patch/delete` typed helpers
  1112→  1112→- **No retry, no timeout, no abort, no multipart/form-data helper**

  1653→  1653→## 18. Known Issues & Gotchas
  1654→  1654→
  1655→  1655→### Environment
  1656→  1656→1. **`.env` reverts to SQLite** — the `predev` script guards against this, but always verify before starting. If it happens, restore from DOCKER.md reference or git history.
  1657→  1657→2. **DB latency** — Mumbai region (~100ms per query from sandbox). Performance optimizations (fire-and-forget, parallel queries, single-JOIN getWorkspace) have been applied. The `/api/auth/me` route is still slow (500-1000ms) due to 5-6 Prisma round-trips — see §16 item 19.
  1658→  1658→3. **Turbopack instability** — dev server can hang during compilation in the sandbox (memory issue). Clear `.next/` cache and restart.
  1659→  1659→4. **Hydration mismatch from browser extensions** — Grammarly injects `data-gr-ext-installed` + `data-new-gr-c-s-check-loaded` attributes into `<body>`. Fixed via `suppressHydrationWarning` on `<body>` in `layout.tsx`. If new hydration errors appear, check for other browser-extension-injected attributes.
  1660→  1660→
  1661→  1661→### Bundling
  1662→  1662→5. **Do NOT add module-scope `import()` maps** — a `ROUTE_CHUNK_LOADERS` map with 55 `() => import(...)` entries caused Turbopack to create 55 duplicate chunks (+1,303 KB). The ONLY place each route's code should be imported is the `dynamic()` call in `page.tsx`. See §11.1 warning.
  1663→  1663→
  1664→  1664→### Integrations
  1665→  1665→6. **PostEx bulk tracking API** — intermittently returns HTTP 400. Handled with single-track fallback
  1666→  1666→7. **Vercel cron doesn't fire** — on long-lived server. In-process poller added for PostEx (30min). Other crons (city sync, scan reports, Leopard safety-net) need manual triggering or external scheduler. The `ENABLE_IN_PROCESS_POLLER` env var (default `true`) can disable the poller for multi-replica deployments.
  1667→  1667→8. **PostEx API lag** — parcels may be physically picked up but PostEx's API still shows "Booked" for hours. This is a PostEx issue, not FlowOps
  1668→  1668→
  1669→  1669→### Schema
  1670→  1670→9. **SQL functions must be applied manually** — `generate_order_number()`, `normalize_phone()`, etc. are NOT in the Prisma schema. They must be applied via raw SQL to the DB (they were lost during DB migration). A consolidated file `supabase/functions-only.sql` contains all 23 functions + 2 sequences + 12 triggers.
  1671→  1671→10. **No DB-level RLS** — all multi-tenant isolation is in the app layer. A bug in `getWorkspace()` or a missing `companyId` filter could leak data across tenants
  1672→  1672→11. **No `available` column** — `available = onHand - reserved` is computed in app code every time
  1673→  1673→
  1674→  1674→### Performance
  1675→  1675→12. **Audit/metric writes are fire-and-forget** — on a serverless platform (Vercel Edge), these would be killed mid-flight. The current long-lived Bun server keeps them alive
  1676→  1676→13. **`executeLoggedIntegrationAction` has a blocking DB write** — the `IntegrationActionLog` insert in the `finally` block is awaited (~150ms per booking). Not yet converted to fire-and-forget
  1677→  1677→14. ~~**`/api/auth/me` takes 500-1000ms**~~ **FIXED (Phase 1 + Phase 2)**: `buildSessionPayload()` now uses a single raw SQL JOIN (`prisma.$queryRaw`) instead of 5-6 sequential Prisma queries. Latency reduced from ~696ms avg to ~210ms warm (67% faster). The raw query JOINs Profile + UserSetting + Employee + Company + Role + RolePermission in one statement. See `src/lib/session-payload.ts`. Phase 2: client-side stale-while-revalidate caching added via TanStack Query (`refetchOnWindowFocus: true` scoped to session query only — see §11.1). Server-side in-memory cache deliberately deferred (see §16 item 19 note).
