    37→## 1. Executive Summary
    38→
    39→**FlowOps** is a multi-tenant SaaS ERP built for Pakistani e-commerce businesses. It manages the complete order lifecycle: product catalog → customer management → order creation → inventory reservation → courier booking → dispatch → delivery/RTO → returns/exchanges. It integrates with Pakistani courier services (PostEx, Leopard) for real-time booking and status tracking.
    40→
    41→**Core value proposition**: One system to manage products, inventory, orders, customers, and courier bookings — replacing the spreadsheets + WhatsApp + manual courier portal workflow that Pakistani e-commerce sellers currently use.
    42→
    43→**Scale**: 68 Prisma models, 170+ API routes, ~160 React components (108 non-UI + 52 shadcn/ui), 21 SQL migrations, 30 permission keys, 2 live courier integrations, 5 cron jobs.
    44→
    45→**Performance posture** (as of latest optimization pass):
    46→- First Load JS: **1,070 KB** (down from 3,148 KB baseline — 66% reduction via code-splitting)
    47→- Total JS across all chunks: **4,665 KB** (95 chunks — was 10 chunks pre-split)
    48→- All 70 data-fetching views use TanStack Query (was 64/70 — 6 migrated from raw `useEffect`+`api.get()`)
    49→- `React.memo` used on leaf components in 6 largest views
    50→- 10 dead dependencies removed (node_modules: 1.2 GB, was 1.3 GB)
    51→- Route-aware `LoadingFallback` renders PageHeader text immediately at Suspense boundary
    52→- Idempotency system: `withIdempotency()` + `useIdempotentMutation()` on ALL 24+ creation endpoints
    53→- Phone validation: libphonenumber-js for international phone format validation
    54→- Courier cancel: Leopard cancellation now works (guard removed); order cancellation auto-cancels courier booking
    55→- City propagation: corrected cities propagate back to CustomerAddress
    56→- IntegrationActionLog now logs request payloads (not just responses)

    60→## 2. What FlowOps Is
    61→
    62→### Target User
    63→Pakistani e-commerce sellers (Instagram/Facebook/Daraz/Shopify) who:
    64→- Sell products COD (Cash on Delivery) — the dominant payment method in Pakistan
    65→- Ship via local couriers (PostEx, Leopard, TCS)
    66→- Need to track which orders are confirmed, packed, dispatched, delivered, or returned (RTO)
    67→- Need inventory management (stock-based + made-to-order)
    68→- Need customer management with RTO-rate flagging (high-return customers)
    69→
    70→### Multi-Tenant Model
    71→```
    72→Organization (top-level tenant, owned by one user)
    73→  └── Company (sub-tenant — a brand/store under the org)
    74→        ├── Employees (users with roles/permissions in this company)
    75→        ├── Products (company subscribes to org-level product templates)
    76→        ├── Inventory (company-owned stock in locations)
    77→        ├── Orders (company's orders)
    78→        ├── Customers (org-level, shared across companies in the org)
    79→        └── Integrations (company's courier connections)
    80→```
    81→
    82→A user can belong to multiple companies (via Employee records) and switch between them using the workspace switcher. The active company is stored in `UserSetting.activeCompanyId`.
    83→
    84→### Order Lifecycle (the heart of the system)
    85→```
    86→pending → confirmed → processing → packed → dispatched → delivered
    87→                ↓                                      ↓
    88→         partially_backordered                       rto
    89→                ↓
    90→            cancelled
    91→```
    92→
    93→Every transition has inventory side-effects:
    94→- **Confirm**: reserve stock (`reserved += qty`) or backorder if insufficient
    95→- **Dispatch**: deduct stock (`onHand -= qty`, `reserved -= qty`)
    96→- **Cancel**: unreserve stock (`reserved -= qty`)
    97→- **RTO**: restock (`onHand += qty` via `return_resellable` or `return_stitched_received`)

   169→## 4. Architecture Overview
   170→
   171→### High-Level Data Flow
   172→```
   173→Browser (SPA at /)
   174→  ↓ Authorization: Bearer <token> + cookie
   175→Caddy Gateway (:81 → :3000)
   176→  ↓
   177→Next.js 16 API Routes (148 routes under src/app/api/)
   178→  ↓
   179→Server Actions (src/lib/actions/*.ts)
   180→  ↓
   181→Prisma Client (src/lib/db.ts)
   182→  ↓
   183→Supabase PostgreSQL (Mumbai)
   184→```
   185→
   186→### Key Architectural Decisions
   187→
   188→1. **Single SPA route** — the entire app lives at `/` (`src/app/page.tsx`). Navigation is client-side via Zustand's `navigate(route)` with URL sync. There are no other Next.js pages.
   189→
   190→2. **Custom HMAC sessions** — Sessions are HMAC-signed tokens: `userId.timestamp.hmac` (30-day TTL). Dual-channel: `Authorization: Bearer` header (works in iframes/cross-origin) + HttpOnly cookie fallback. (`next-auth` was previously installed but unused; it was removed in Step 4 — see §3.)
   191→
   192→3. **Multi-tenant isolation in app layer** — `getWorkspace()` in `src/lib/workspace.ts` resolves the caller's active company from `UserSetting.activeCompanyId` via a SINGLE Prisma JOIN query (Profile → settings.activeCompany + employees.role). No database-level RLS — all scoping is enforced in the application layer via `requirePermission()`.
   193→
   194→4. **Fire-and-forget audit/metric writes** — `insertAuditLog()` and `insertMetricEvent()` return `void` immediately (detached promises via `fireAndForget()`). This works because the app runs on a long-lived Bun/Node server where the event loop survives the HTTP response.
   195→
   196→5. **Adapter pattern for couriers** — provider-agnostic `CourierAdapter` interface. Only PostEx + Leopard are real implementations; TCS is a stub. All courier calls go through `executeLoggedIntegrationAction()` which logs every API call to `integration_action_logs`.
   197→
   198→6. **Prisma `db push` workflow** — the `supabase/migrations/*.sql` files are reference SQL. The live schema is managed via `prisma db push` against `prisma/schema.prisma`. SQL functions (like `generate_order_number()`) must be applied manually to the DB.

   360→## 6. Authentication & Multi-Tenancy
   361→
   362→### Session System
   363→- **Token format**: `userId.timestamp.hmac` (HMAC-SHA256 signed)
   364→- **TTL**: 30 days
   365→- **Storage**: `localStorage` key `flowops_session_token` + HttpOnly cookie `flowops_session`
   366→- **Dual-channel**: API client sends BOTH `Authorization: Bearer <token>` header AND cookie — works in iframes, cross-origin, and same-origin
   367→
   368→### Auth Flow
   369→```
   370→1. POST /api/auth/login {email, password}
   371→2. Server: verify scrypt hash → create session token → set cookie + return token
   372→3. Client: store token in localStorage + Zustand store
   373→4. Subsequent requests: send Bearer token + cookie
   374→5. POST /api/auth/logout → clear cookie + localStorage
   375→```
   376→

   394→### Workspace Resolution
   395→`getWorkspace()` in `src/lib/workspace.ts`:
   396→- Resolves caller's active company + employee + role in a SINGLE Prisma query (Profile → settings.activeCompany + employees.role)
   397→- Throws `ApiError(401)` if not signed in, `ApiError(403)` if no active company or not a member
   398→- Returns `WorkspaceContext` = `{ user, employee, company }`
   399→- Called by nearly every authenticated API route
   400→
   401→### Session Payload (`src/lib/session-payload.ts`)
   402→`buildSessionPayload()` uses a SINGLE raw SQL JOIN (`prisma.$queryRaw`) that joins Profile + UserSetting + Employee + Company + Role + RolePermission in one statement. Replaces the previous 5-6 sequential Prisma queries. Latency: ~696ms → ~210ms warm (67% faster). The raw query result (flat rows) is grouped in JS back into the nested SessionResponse shape. The old SQL `normalize_phone()` function remains for DB-level triggers/matching; the app-layer path now uses `libphonenumber-js` for phone normalization.

  1012→
  1013→### Architecture
  1014→```
  1015→API Route / Server Action
  1016→  ↓
  1017→executeLoggedIntegrationAction({ fn: () => adapter.method() })
  1018→  ↓ logs to IntegrationActionLog
  1019→CourierAdapter (interface)
  1020→  ↓
  1021→PostExAdapter | LeopardAdapter | TcsAdapter (stub)
  1022→  ↓
  1023→External Courier API
  1024→```
  1025→
  1026→### `executeLoggedIntegrationAction()` — request payload logging
  1027→Now accepts optional `requestPayload` parameter — stores the actual request data sent to the courier (e.g., delivery city, address, COD amount) in `IntegrationActionLog.requestPayload`. Previously this was always null.
  1028→
  1029→All outbound calls now log their request payload:
  1030→- `book_shipment` (full BookShipmentInput)
  1031→- `cancel_shipment` (trackingNumber + providerKey)
  1032→- `track_shipment` (trackingNumber)
  1033→- `track_shipment_bulk` (trackingNumbers array)
  1034→- `generate_load_sheet` (trackingNumbers + pickupAddress)
  1035→- `create_pickup_address` (address data)
  1036→
  1037→No credentials are logged — only business data.

  1095→## 11. Frontend Architecture
  1096→
  1097→### 11.1 Single-Page App Structure
  1098→
  1099→The entire app is a **single Next.js page** at `/` (`src/app/page.tsx`). All "pages" are route cases inside a `switch(route.name)` in `renderRoute()`.
  1100→
  1101→**Code-splitting strategy** (Step 1 optimization — August 2026):
  1102→All 70+ view components are lazy-loaded via `next/dynamic` with `ssr: false`:
  1103→```typescript
  1104→const ProductsView = dynamic(
  1105→  () => import('@/components/products/products-view').then(m => ({ default: m.ProductsView })),
  1106→  { ssr: false, loading: LoadingFallback }
  1107→)

  1126→
  1127→**Pre-switch gating logic:**
  1128→1. **Hydration via TanStack Query**: On mount, `useQuery(['session', 'me'])` fires `GET /api/auth/me`. This query has a **deliberate per-query override**: `refetchOnWindowFocus: true` (the global default is `false`). Session validity (active employee status, permissions, platform-level access) is the one place where catching a change quickly after the user returns to a background tab matters — e.g., an employee terminated while their tab sat in the background should see their UI reflect that promptly on refocus. Every other view stays on the global `false` default because they display data, not gate security-sensitive UI. The query result is wired into `useAppStore.setSession()` via a `useEffect` — first fetch shows a loading spinner, background refetches update the store silently (only if data changed). If URL has `?view=...`, restores that route. Listens to `popstate` for browser back/forward.
  1129→2. **Loading screen**: `<Loader2 className="animate-spin">` while `!hydrated` (first session fetch only — background refetches do NOT show a spinner).
  1130→3. **Unauthenticated** (`!user`): login/register/forgot/reset forms, all wrapped in `AuthShell`.
  1131→4. **Authenticated but not onboarded**: `OnboardingView` / `CreateOrganizationView` / `CreateCompanyView`.
  1132→5. **Authenticated + onboarded**: `<DashboardShell>{renderRoute(route)}</DashboardShell>`.

  1707→## 17. Key Conventions & Patterns
  1708→
  1709→### Naming
  1710→- **Tables**: PascalCase (Prisma default) — `Order`, `OrderItem`, `InventoryPool`
  1711→- **Columns**: camelCase (Prisma default) — `flowopsOrderNumber`, `courierSubStatus`
  1712→- **API routes**: kebab-case — `/api/booking-workbench/bookable`
  1713→- **Files**: kebab-case — `order.actions.ts`, `postex.adapter.ts`
  1714→- **Components**: PascalCase — `OrderDetailView`, `BookingWorkbenchView`
  1715→
  1716→### Status Enums (all plain strings, no DB enums)
  1717→- **Order.status**: `pending | confirmed | partially_backordered | processing | dispatched | delivered | rto | cancelled | refunded`
  1718→- **OrderItem.fulfillmentStatus**: `pending | reserved | backordered | dispatched | returned`
  1719→- **courierSubStatus**: `slip_generated | pickup_requested | picked_up | at_warehouse | en_route | out_for_delivery | delivered | returned | out_for_return | attempted | under_review | cancelled_by_merchant | expired`
  1720→- **courierBookingStatus**: `not_booked | booked | failed | cancelled`
  1721→- **paymentStatus**: `cod_pending | advance_paid | fully_prepaid | cod_collected`
  1722→- **fulfillmentType**: `stock_based | made_to_order`
  1723→- **inventoryPolicy**: `deny | continue`
  1724→
  1725→### Fire-and-Forget Pattern
  1726→```typescript
  1727→// insertAuditLog + insertMetricEvent return void immediately
  1728→// The DB write happens on the event loop AFTER the response is sent
  1729→insertAuditLog({ action: 'order.created', ... })  // no await!
  1730→insertMetricEvent({ metricKey: 'order.created', ... })  // no await!
  1731→```
  1732→
  1733→### Workspace Context Pattern
  1734→```typescript
  1735→// Every authenticated API route starts with:
  1736→const ctx = await getWorkspace()  // resolves user + employee + company
  1737→await requirePermission(ctx, PERMISSIONS.ORDERS_CREATE)  // throws 403 if lacking
  1738→```
  1739→
  1740→### Adapter Pattern
  1741→```typescript
  1742→// Never call adapter methods directly — always through executeLoggedIntegrationAction:
  1743→const result = await executeLoggedIntegrationAction({
  1744→  companyIntegrationId: integration.id,
  1745→  organizationId: ctx.company.organizationId,
  1746→  actionType: 'book_shipment',
  1747→  direction: 'outbound',
  1748→  fn: async () => adapter.bookShipment(bookInput),
  1749→})
  1750→// This logs the call to IntegrationActionLog + handles errors
  1751→```
  1752→
  1753→### Idempotency
  1754→- `reserveOrderStock` skips items with `fulfillmentStatus === 'reserved'` or `'dispatched'`
  1755→- `performOrderDispatch` skips items already `'dispatched'`
  1756→- `restockOrderForRto` skips items already `'returned'`
  1757→- `processInventoryTransaction` validates stock before mutating
  1758→
  1759→### Creation Idempotency (withIdempotency pattern)
  1760→```typescript
  1761→// ALL creation endpoints wrap their action in withIdempotency():
  1762→const { result, wasReplay } = await withIdempotency({
  1763→  key: idempotencyKey,          // from Idempotency-Key header
  1764→  companyId: ctx.company.id,
  1765→  employeeId: ctx.employee.id,
  1766→  actionType: 'order.create',   // or 'product.create', 'customer.create', etc.
  1767→  fn: async () => { /* actual creation logic */ },
  1768→})
  1769→// DB unique constraint on key enforces atomicity — no race window
  1770→// Failed attempts can be retried with the same key
  1771→// Stale 'processing' rows (>60s) auto-recover
  1772→```
  1773→
  1774→### Phone Validation (libphonenumber-js)
  1775→```typescript
  1776→// Client-side: isValidPhoneFormat(phone) blocks submission
  1777→// Server-side: validateAndNormalizePhone(phone) returns { isValid, normalized }
  1778→// External platform: isValidFormat=false on CustomerPhone row (not blocked)
  1779→// International: normalize_phone() SQL has pass-through fix for + non-PK numbers
  1780→// matchOrCreateExternalCustomer: pre-normalizes international numbers via libphonenumber-js before SQL call
  1781→import { isValidPhoneFormat, validateAndNormalizePhone } from '@/lib/phone-validation'
  1782→```
  1783→
  1784→### Country System
  1785→- `CustomerAddress.country` + `Order.deliveryCountry` store ISO 3166-1 alpha-2 codes (e.g. "PK", "GB"), defaulting to "PK"
  1786→- `CountrySelector` component (reusable) returns alpha-2 codes directly
  1787→- Non-PK addresses skip courier city-matching (matchCity, revalidateCityAtBookingTime, validateCustomerAddressCity all early-return for non-PK)
  1788→- Phone validation uses the address's country as a HINT for no-`+`-prefix numbers (never a hard rule)
  1789→- Shopify fallback: `country_code → countryNameToCode(country) → customer.addresses[0].country → Company.countryCode → 'PK'`
  1790→
  1791→### Self-Fulfilled Channel
  1792→- `Order.fulfillmentChannel`: `'courier' | 'self_fulfilled'` (default `'courier'`)
  1793→- Auto-defaults to `'self_fulfilled'` when `deliveryCountry !== 'PK'` (always overridable)
  1794→- `generate_self_fulfilled_reference(companyId)` SQL: per-company MAX-based `SF-YYYY-NNNNN`
  1795→- Self-fulfilled orders skip auto-booking + city-courier-matching entirely
  1796→- Internal slip PDF: jsbarcode CODE128 barcode → SVG → sharp → PNG → @react-pdf/renderer
  1797→- `processScan()` resolves via `OR: [trackingNumber, selfFulfilledReferenceNumber]`
  1798→- Fully independent of the Markets system (no code coupling)
  1799→
  1800→### Markets System (3-Gate Enforcement)
  1801→- **Gate 1**: `OrgProductVariant.isActive` — toggled-off variants appear DISABLED in picker (not hidden)
  1802→- **Gate 2**: `MarketProduct` enablement for the resolved market
  1803→- **Gate 3**: `MarketVariantPricing` exists for this variant + resolved market
  1804→- First failing reason only (priority: gate 1 → 2 → 3)
  1805→- Manual orders: blocked if country not in any market (server-side rejection)
  1806→- External orders: NEVER blocked — flagged with `needsReview` + `needsReviewReason`
  1807→- Payment types restricted to market's `allowedPaymentTypes` (client + server enforcement)
  1808→- No fallback anywhere — a variant with no explicit market price is simply not sellable
  1809→
  1810→### Pricing Resolution (Discount Rework)
  1811→- `unit_price` is NO LONGER accepted from the client (removed from schema)
  1812→- Server resolves `originalUnitPrice` STRICTLY from `MarketVariantPricing` for the resolved market
  1813→- If no MVP row exists → server REJECTS with gate-3 error (no CompanyVariantPricing/costPrice fallback)
  1814→- Per-item discount (`discountType`/`discountValue`): percentage (0-100) or fixed (≤ originalUnitPrice), clamped at 0
  1815→- `unitPrice = originalUnitPrice - discount` (final charged price)
  1816→- `Order.discountAmount`/`discountReason` (order-wide flat discount) works independently
  1817→
  1818→### Currency Revenue Rollup
  1819→- `computeRevenueWithCurrencies(companyId, orders, baseCurrency)` in `src/lib/analytics/revenue.ts`
  1820→- Returns: `{ perCurrency: Map, estimatedTotalBase, baseCurrency, estimateComplete }`
  1821→- Per-currency breakdown is always accurate (raw sums, no conversion)
  1822→- Estimated total uses latest `ExchangeRateSnapshot` — display only, never touches stored prices
  1823→- Used by all 3 revenue sites: orders-view (via `/api/orders/revenue-summary`), order-funnel.ts, customer.actions.ts

  1827→## 18. Known Issues & Gotchas
  1828→
  1829→### Environment
  1830→1. **`.env` reverts to SQLite** — the `predev` script guards against this, but always verify before starting. If it happens, restore from DOCKER.md reference or git history.
  1831→2. **DB latency** — Mumbai region (~100ms per query from sandbox). Performance optimizations (fire-and-forget, parallel queries, single-JOIN getWorkspace) have been applied. `/api/auth/me` is now ~210ms (was 500-1000ms) — FIXED (see item 14 for details).
  1832→3. **Turbopack instability** — dev server can hang during compilation in the sandbox (memory issue). Clear `.next/` cache and restart.
  1833→4. **Hydration mismatch from browser extensions** — Grammarly injects `data-gr-ext-installed` + `data-new-gr-c-s-check-loaded` attributes into `<body>`. Fixed via `suppressHydrationWarning` on `<body>` in `layout.tsx`. If new hydration errors appear, check for other browser-extension-injected attributes.
  1834→
  1835→### Bundling
  1836→5. **Do NOT add module-scope `import()` maps** — a `ROUTE_CHUNK_LOADERS` map with 55 `() => import(...)` entries caused Turbopack to create 55 duplicate chunks (+1,303 KB). The ONLY place each route's code should be imported is the `dynamic()` call in `page.tsx`. See §11.1 warning.
  1837→
  1838→### Integrations
  1839→6. **PostEx bulk tracking API** — intermittently returns HTTP 400. Handled with single-track fallback
  1840→7. **Vercel cron doesn't fire** — on long-lived server. In-process pollers added for PostEx (30min) + exchange rate refresh (24h). Other crons (city sync, scan reports, Leopard safety-net) need manual triggering or external scheduler. The `ENABLE_IN_PROCESS_POLLER` + `ENABLE_IN_PROCESS_FX_REFRESH` env vars (default `true`) can disable for multi-replica deployments.
  1841→8. **PostEx API lag** — parcels may be physically picked up but PostEx's API still shows "Booked" for hours. This is a PostEx issue, not FlowOps
  1842→
  1843→### Schema
  1844→9. **SQL functions must be applied manually** — `generate_order_number()`, `generate_self_fulfilled_reference()`, `normalize_phone()` (with international pass-through fix), `match_or_create_customer()` (now 7 params), etc. are NOT in the Prisma schema. They must be applied via raw SQL to the DB. A consolidated file `supabase/functions-only.sql` contains all 24+ functions + 2 sequences + 12 triggers + 2 partial unique indexes (`invitation_pending_email_unique` + `market_one_default_per_company`).
  1845→10. **No DB-level RLS** — all multi-tenant isolation is in the app layer. A bug in `getWorkspace()` or a missing `companyId` filter could leak data across tenants
  1846→11. **No `available` column** — `available = onHand - reserved` is computed in app code every time
  1847→12. **Order-create child components are module-level functions** — `CustomerSection`, `ItemsSection`, `PaymentSection`, etc. in `order-create-view.tsx` are declared at the module level (NOT closures inside `OrderCreateView`). Any new state variable used in these child components MUST be passed as a prop — referencing it directly will compile fine but crash at runtime with `ReferenceError`. TypeScript does NOT catch this. When adding new state/hooks to `OrderCreateView` that child components need, always: (1) add it to the child's destructured props, (2) add it to the child's type definition, (3) pass it from `<OrderCreateView>` to `<ChildComponent>`.
  1848→
  1849→### Performance
  1850→13. **Audit/metric writes are fire-and-forget** — on a serverless platform (Vercel Edge), these would be killed mid-flight. The current long-lived Bun server keeps them alive
  1851→14. **`executeLoggedIntegrationAction` has a blocking DB write** — the `IntegrationActionLog` insert in the `finally` block is awaited (~150ms per booking). Not yet converted to fire-and-forget
  1852→15. ~~**`/api/auth/me` takes 500-1000ms**~~ **FIXED (Phase 1 + Phase 2)**: `buildSessionPayload()` now uses a single raw SQL JOIN (`prisma.$queryRaw`) instead of 5-6 sequential Prisma queries. Latency reduced from ~696ms avg to ~210ms warm (67% faster). The raw query JOINs Profile + UserSetting + Employee + Company + Role + RolePermission in one statement. See `src/lib/session-payload.ts`. Phase 2: client-side stale-while-revalidate caching added via TanStack Query (`refetchOnWindowFocus: true` scoped to session query only — see §11.1). Server-side in-memory cache deliberately deferred (see §16 item 19 note).
  1853→16. **Booking-time city corrections were not persisted** (FIXED) — `order.update` in `bookOrderWithCourier()` now includes `deliveryCity` + `deliveryAddress`. Pre-fix, corrected cities were sent to the courier API but not saved on the Order row. Historical data cannot be backfilled (requestPayload was null for pre-fix logs). Going forward, requestPayload is logged for all outbound calls.
  1854→17. **Employee invite had race window** (FIXED) — was check-then-create (findFirst then create). Now has partial unique index `invitation_pending_email_unique` on `(companyId, invitedEmail) WHERE status='pending'` + catches P2002 constraint violation.
  1855→18. **Company integration had race window** (FIXED) — was find-then-create. Now has `@@unique([companyId, providerId])` + catches P2002 → re-fetches + reactivates.
